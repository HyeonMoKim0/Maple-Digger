## 1. 개요

프로그램을 **실행하기 전에**, 조립한 블록들이 일꾼을 실제로 어떤 경로로 움직이게 하는지 **광산 맵 위에 미리 보여준다**. 편집기의 블록 칸과 맵 위 표시가 **같은 번호**로 짝지어져, "몇 번째 블록이 어디서 무엇을 하는지"를 실행 없이 한눈에 검토할 수 있다.

목업 예시 — 프로그램 `동 E, 동 E, 동 E, 북 N, 북 N, 남 S, 남 S` (7블록):

- 편집기 스트립: 각 칸 위에 **순번 1~7** 표기.
- 맵: 일꾼 현재 위치를 기점으로, 각 이동 블록이 도착하는 타일에 **번호 + 방향 문자**(`1 E`, `2 E`, … `5 N`)가 붙은 마커 표시.
- 같은 타일을 두 번 지나는 경우(4↑ 후 6↓, 3→ 후 7↓)는 **한 타일 안에 마커를 나란히** 배치한다.

## 2. 표시 규칙

### 2.1 번호 매기기

- 프로그램의 **평탄 토큰 순서**(스트립 칸 순서 그대로, docs/28 §2.1)로 1부터 순번을 붙인다.
- 편집기 스트립 칸과 맵 마커가 **동일 번호**를 공유한다 — 번호가 곧 두 화면을 잇는 링크다.

### 2.2 맵 마커

- **이동 블록**(동/서/남/북): 그 블록 실행 후 일꾼이 **도착하는 타일**에 `번호 + 방향 문자` 마커.
- **행동 블록**(채굴 M · 적재 L · 하역 U) — **확정(2026-08-25)**: 행동이 일어나는 **제자리 타일**에 `번호 + 행동 문자` 마커를 표시한다. 이동 마커와 같은 타일이면 §2.3 겹침 규칙으로 나란히 배치.
- **반복 블록** — **확정(2026-08-25)**: 몸통 **1회분 경로만** 그리고, 해당 마커에 `×N` 반복 표기를 병기한다. 반복 횟수만큼 전부 펼치지 않는다 — 마커 폭증을 원천 차단.
- **IF 블록** — **확정(2026-08-25)**: 미리보기 시점의 **실제 맵 상태(광물 유무)로 조건을 실제 판정**하여 그 결과 경로를 그린다. 가장 정확한 방식이나, 실행 시점까지 맵이 변하면 미리보기와 실제가 어긋날 수 있음은 감수(미리보기는 표시 전용이므로 허용).
- 시뮬레이션 기점은 **선택된 일꾼의 현재 위치·현재 적재 상태**다. 경로 계산은 클라이언트 로컬 표시 전용 — 서버 검증(Run 시점 `ValidateProgram`)과 무관하며 권위를 갖지 않는다.

### 2.3 겹침 처리 (같은 타일을 여러 번 지날 때)

- 한 타일에 마커가 2개 이상이면 **타일 내부에서 자리를 비켜 나란히** 배치한다 (목업의 `4·6`, `3·7`).
- 타일 내부 공간이 부족하면 **한 줄(행)을 건너뛰어** 다음 줄에 이어서 배치한다.
- **확정(2026-08-25)**: 그래도 넘치면(타일당 상한 초과, 예: 4개) 마지막 마커를 **`+N` 접기**로 축약한다 — 스트립 그리드의 `+N` 접기(docs/28 §2.2)와 일관된 규칙. 타일당 상한 값은 구체화 시 확정.

### 2.4 표시 시점 (핵심 계약)

| 상태 | 미리보기 |
|---|:--:|
| 편집 중 / 실행 전 (Idle·프로그램 유효) | **표시** |
| **실행 중 (Running)** | **숨김** |
| **정지 (Stop 후)** | **표시** (현재 위치 기준으로 재계산) |

- **갱신 시점 — 확정(2026-08-25)**: 블록 **추가/삭제 즉시** 자동 재계산한다. 별도 "미리보기" 조작을 두지 않는다.
- 실행 중에는 미리보기를 지워 실제 이동 연출과 겹치지 않게 한다. 실행 중 "지금 어느 스텝인지"는 docs/28 U4(스트립 셀 강조)의 몫 — 두 기능이 실행 전/실행 중을 분담한다.
- 정지 시점의 일꾼 위치가 기점이므로, 중단 후 재검토 → 수정 → 재실행 흐름을 지원한다.

### 2.5 범위·비주얼

- **다중 일꾼 — 확정(2026-08-25)**: **선택된 일꾼 1명**의 프로그램만 표시한다. 워커 탭 전환 시 그 일꾼 기준으로 갱신.
- **화면 밖 경로 — 확정(2026-08-25)**: 마커는 월드 좌표에 그대로 배치하고 **추가 처리 없음** — 플레이어가 캐릭터를 움직여 카메라가 따라가면 자연스럽게 보인다. 가장자리 화살표·카메라 자동 이동은 하지 않는다.
- **마커 비주얼 — 확정(2026-08-25)**: 목업의 빨간 테두리는 의도 전달용이며 확정안이 아니다. 실제 마커는 **반투명 고스트 타일**(타일 위 반투명 오버레이) + 번호·문자로 간다 — 맵을 덜 가리는 부드러운 표현. 구체 자산은 docs/20·21 승인 절차를 거친다(그림 단독 금지 — 문자 병기 원칙은 충족).

## 3. 기대 효과

- **실행 전 검증**: 벽에 부딪히거나 광맥을 지나치는 프로그램을 실행 없이 발견 → D-17류 "실수 후 처음부터 재조립" 비용 감소.
- **학습 보조**: 튜토리얼에서 블록↔실제 이동의 대응을 말이 아니라 그림으로 보여줄 수 있다 (docs/19 접점 — 구체화 시 확인).
- **번호 링크**: 스트립 칸 클릭-삭제(docs/28 §2.3)와 결합하면 "맵에서 잘못된 지점을 보고 → 같은 번호 칸을 삭제"하는 왕복 편집이 가능해진다.

## 4. 기존 시스템과의 접점 (구체화 시 확인)

- **표시 구현**: 맵 마커는 월드 엔티티(타일 위 반투명 스프라이트 + 번호)다. 고정 풀 미리 생성 + 런타임 스왑 패턴(워커 탭·스트립 36칸과 동일)이 자연스럽다. 반복 ×N 병기 확정으로 마커 수 상한이 "블록 상한 30 + 겹침 +N 접기" 수준으로 유계 — 풀 크기 산정이 단순해졌다.
- **경로 시뮬레이션**: 클라이언트에 이동/충돌 규칙의 사본이 필요하다. IF를 실제 맵 상태로 판정하기로 확정했으므로 **광물 유무 판정 규칙도 클라이언트에서 참조 가능**해야 한다. `VeinTickSimulator`(서버)와 규칙이 어긋나면 미리보기가 거짓말을 하므로, 규칙 함수를 공용 모듈로 분리하는 방안 검토.
- **즉시 갱신 성능**: 편집 즉시 재계산 확정 — 블록 추가/삭제 1회당 시뮬레이션 1회(최대 30블록 + 반복 1회분)라 비용은 미미할 것으로 예상. docs/24 성능 기준에서 확인.
- **스트립 번호 표기**: 기존 56×56 셀(docs/28 §2.2)에 순번 오버레이 추가 — 셀 구조 변경 없이 텍스트 1개 추가 수준인지 확인.

### 2차 PR 구현 기록 (2026-08-25, 브랜치 `feat/t16-preview-control`)

| 항목 | 내용 |
|---|---|
| 반복 ×N | 몸통 1회분만 전개하고 마커에 `×N` 병기 (`inf` → `∞`). **중첩 반복은 가장 안쪽 ×N만 병기** — 곱 표기는 읽기 부담 대비 이득이 없어 채택하지 않음 (2026-08-25 구현 결정, §6-1 해소) |
| IF 실제 판정 | `EvaluateCondition` 클라 재현 — 광물 유무는 VeinMarker @Sync(ReserveStage, 특별은 IsActive 병행) 스냅샷, 수레는 @Sync CartCount/Capacity. 시뮬레이션 중 채굴·적재·하역이 로컬 상태(손·수레·광맥 잔량)를 갱신해 뒤따르는 IF 에 반영 (행운 yield 확률은 배제 — 결정적 미리보기) |
| +N 접기 | 타일당 5개째부터 4번째 슬롯이 `+N` 회색 마커(스트립 overflow 와 같은 계열)로 축약 |
| 순번 부여 | 반복·IF 토큰이 끼면 "스텝 순서 ≠ 스트립 인덱스"가 되므로, `FlattenList` 토큰의 **노드 참조 역인덱스**로 순번을 부여한다 (`BlockProgramController.GetStrip` 신설) |
| 실측 통과 | 시나리오 A: `1E · 3M×3 · 4L×3 · 12N` — IF 광물없음/수레안참 분기 몸통 스킵 + 제어 토큰 포함 순번 일치. 시나리오 B: IF 참 분기 포함 + 같은 타일 5개 → shown=4(+2 접힘). 시각: 한 타일 2×2 에 `1W / 3M ×3 / 5M / +2` 렌더 확인 |

**플랫폼 실측 노트 (다음 세션 주의)**
- 월드 텍스트는 **`TextRendererComponent`** 다. `TextComponent` 는 UI 전용 레거시라 월드 엔티티에 붙으면 **무렌더 무오류**(실측). 워커 칩(UI)의 TextComponent 선례를 월드로 옮기면 안 된다.
- `TextRendererComponent.FontSize` 는 UI 픽셀이 아니라 **월드 스케일 기준** — 46이면 화면 전체를 덮는다. 정상 범위는 한 자리 수(단독 3 / 겹침 1.8).
