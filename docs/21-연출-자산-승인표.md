## 1. 광맥 — 핵심 발견

검색 결과 **광맥 stage 표현에 그대로 쓸 수 있는 자산 2개**를 찾았다. 둘은 역할이 달라 **함께 쓰는 것**을 권한다.

> ⚠️ **2026-07-31 육안 검증으로 정정.** `condition1~5`는 **깔끔한 5단계 잔량 램프가 아니다.** 실제로는 **청록 결정 5종(크기 차이) + `condition2` 하나만 빨강 색상 변종**이다. 따라서 `condition2`는 잔량 램프에서 빼야 하고, 남는 청록 5종에서 4개를 고른다. 근거는 §6.2.

**관측된 잔량 순서** (많은 것 → 적은 것, §6.2 스크린샷 기준):

```
stand ≈ condition1  >  condition3 ≈ condition4  >  condition5
```

**확정 매핑** (2026-07-31 오너 승인 · D8 **C206**)

| `ReserveStage` | 의미 | 자산 | RUID |
|:-:|---|---|---|
| 3 | 만재 | `condition1` | `0f44530d655f4e33bfbe43423450ee9f` |
| 2 | — | `stand` | `a0bd28cbdcd54445827f0375f24266b5` |
| 1 | — | `condition4` | `2daf76debab042e09b2d3bf2d5ba575f` |
| 0 | 고갈 | `condition5` | `40c805ead61d440889632ef2244dab30` |

- `condition3`은 `condition4`와 거의 같은 크기라 미사용으로 남긴다. 관측상 `condition3` > `condition4`이므로 낮은 stage에는 더 작은 `condition4`를 두는 쪽이 내림차순에 맞는다.
- **5단계(청록 5장 전부 사용)는 채택하지 않았다.** `VeinTickSimulator.MaxReserveStage`를 3→4로 올려야 하는데, 광맥당 채굴 3→4회(**+33%**)·완전 회복 15→20틱으로 경제 밸런스가 바뀐다. **`MaxReserveStage = 3`(stage 0~3, 4단계) 유지**가 확정이다 (C206).
- **`stand`과 `condition1`의 차이가 작다**(둘 다 큰 결정 + 위성 파편 2개). stage 3↔2 구분이 약하므로, 구분이 부족하면 stage 3에만 `Scale` 미세 증가나 밝기 보정을 얹는 것을 검토한다.
- **`condition2`(빨강)는 잔량 표현에 쓰지 않는다.** 색만 다르고 형태는 같아 D5 §8 **V1**("색 외의 형태로 구분")을 위반한다. 특별 광맥 후보로도 같은 이유로 부적합하다. 희귀 광맥 강조 같은 다른 용도의 후보로만 남긴다.

### 1.3 광물 3종(돌·철·금) 구분 방법 — 결정 필요

위 두 자산은 **광물 종류 구분이 없다.** Q1-ⓐ를 문자 그대로 지키려면 `oreType × stage` **12개 서로 다른 스프라이트**가 필요한데, 그런 자산군은 검색으로 찾지 못했다.

| 방안 | 내용 | 평가 |
|---|---|---|
| A | `부유석` condition 4개를 stage로 쓰고, **광물 종류는 `SpriteRendererComponent.Color` 색조로 구분** | 자산 제작 0. 단 광물 종류가 **색으로만** 구분돼 D5 §8 **V1**("색 외의 형태로 구분")을 광물 축에서 어긴다 |
| B | `msw-painter`로 **12개를 직접 제작** | V1을 완전히 충족. 픽셀아트 12장 제작 비용 |
| **C ✅ 확정** | stage는 `부유석` condition, **광물 종류는 광맥 위에 작은 아이콘 뱃지**를 겹쳐 표시 | 자산 제작 0이면서 종류가 **형태로** 구분된다 |

**C로 확정 (2026-07-30, D8 C205).** D5 §3이 일반 광맥의 표현을 "돌/철/금의 형태·색·**작은 아이콘** + stage 0~3 크기·균열·광택 변화"로 규정하고 있어, 아이콘 뱃지는 기획 원문에 이미 들어 있는 방식이다. 승인된 아이콘(`docs/20` §0)을 그대로 재사용하므로 추가 검색도 필요 없다.

**구현 형태**

- 광맥 엔티티 = 부모(`SpriteRendererComponent` = `부유석` condition, stage에 따라 교체) + **자식 뱃지 엔티티**(`SpriteRendererComponent` = `docs/20` §0의 광물 아이콘).
- 뱃지는 광맥 스프라이트의 **상단**에 작게 얹는다. 크기는 원본 아이콘(28~32px)을 월드 단위로 환산해 약 0.3 unit 내외.
  - **구현 확정 (2026-08-04)**: 부모 로컬 `(0, 0.62)`(일반) / `(0, 0.45)`(특별), `Scale` 1.4. 화면에서는 광맥의 **우상단**에 붙는다 — 부모 자식 좌표에 스프라이트 pivot 이 곱해진 결과다. 광맥을 가리지 않고 종류 식별도 되므로 이 위치로 확정했다. 작성 당시의 "좌상단 또는 상단 중앙"은 실측 전 표현이었다.
- 뱃지는 `oreType`으로만 결정되고 **stage에 따라 바뀌지 않는다.** stage 변화는 부모 스프라이트가 담당한다.
- 뱃지의 `SortingLayer`·`OrderInLayer`를 부모보다 **위**로 둔다. 같은 값이면 가려질 수 있다.
- 고갈(stage 0)에서도 뱃지는 유지한다 — "여기가 무슨 광맥이었는지"를 알아야 플레이어가 회복을 기다릴 수 있다.

AI가 만들 수 있는 증거는 **`PlaySound`/`PlayBGM` 디스패치 로그까지**이고, "어울리는가"는 오너 청취만이 답한다(`docs/16` §9).

**✅ 루프는 확인됐다 (2026-08-14 실측, F10 §3.3).** `IsPlayBGM()`을 10초 간격으로 찍어 `t=10s`부터 `t=200s`까지 전부 `playing=true`를 받았다 — 곡 끝(141.5s)을 **58.5초 넘겨서도 재생 중**이므로 `PlayBGM`은 반복 재생이다. `PlayLoopSound` 대체는 불필요하고 F10 §2.2 경계값 표도 그대로 유효하다. **Phase 6에서 판정할 것은 곡 자체와 볼륨 균형뿐이고, "곡이 끝나고 조용해지는지"는 이미 답이 나왔다.**

### 5.0 이펙트 후보는 텍스트 검색으로 못 찾는다 (2026-08-04)

채굴 파편을 3번째로 고르면서 확인했다. **`searchResources` 로 시각 이펙트를 찾는 것은 사실상 작동하지 않는다.**

- 8가지 질의(한/영)로 39건을 모았는데 **전부 `names` 가 비어 있고 `score` 가 0.000** 이었다. `dname` 도 `sprite-8923707` 같은 일련번호뿐이라 **메타데이터로 걸러낼 근거가 아예 없다.**
- 실제로 띄워 보니 "먼지"로 잡힌 것 중에 **나무 상자**(`6f638bd2`)와 **검은 연기**(`2b74d000`)가 있었다. 검은 연기는 이미 기각한 `d4f82b52`와 같은 실패다.
- 기각 이력이 있는 `d4f82b52`·`6ade17ad` 가 이 검색 결과에 **그대로 다시 올라온다.** 기각 사유를 문서에 남겨 두지 않으면 다음 세션이 같은 것을 또 집는다.

**대신 `findSimilarResources` 를 쓴다.** 이미 옳다고 판정된 자산을 씨앗으로 넣으면 시각적으로 닮은 것을 준다 — `78ea5621`(2차 파편)을 씨앗으로 넣으니 **전부 `skill` 카테고리 애니메이션클립 12개**가 나왔고, 확정된 `de538ed7` 이 그중에 있었다.

> 씨앗을 아무거나 넣으면 안 된다. `신비한 광석 hit1`(`13a63ebb`)을 씨앗으로 넣었더니 `object`/`background` 스프라이트(바위·배경)만 나왔다. **연출은 연출을 씨앗으로** 삼아야 한다.

### 5.0.1 pivot 이 중심이 아닌 스프라이트가 있다

확정된 `de538ed7` 이 그렇다. 광맥 좌표에 그대로 놓으면 **오른쪽으로 밀려서** 뜨고, **엔티티 `Scale` 이 pivot 오프셋까지 함께 키우므로 크기를 키울수록 더 밀린다** — 상수 보정으로는 크기를 바꿀 때마다 어긋난다.

`farm01` 실측: scale 0.9 / 1.3 / 1.7 에서 각각 85 / 125 / 165 px 이동(1 unit = 110 px) → **약 `-0.855 unit × Scale`**. `WorkerVisualController.ShardPivotOffsetX` 가 이 값이고 `MoveShardToCell` 이 `ShardScale` 을 곱해 쓴다. 앞서 쓰던 `78ea5621` 은 pivot 이 거의 중심이라 이 문제가 없었다.

**세로도 따로 잰다 (2026-08-06 추가).** 같은 자산의 Y pivot 도 중심이 아니다 — **`ShardPivotOffsetY = -0.215 unit × Scale`** (`ShardScale` 1.3 에서 -0.28 unit 이 광물 조각을 먼지구름 정중앙에 놓는다). X 만 재고 Y 를 재지 않아 세로 어긋남이 8/6 오너 검수까지 숨어 있었다. **자산을 교체하면 두 축 모두 다시 잰다** — pivot 이 중심인 자산이면 둘 다 0 이다. 측정은 `PlayRate` 0.02 + `StartFrameIndex/EndFrameIndex` 0~1 고정 상태에서 한다(애니메이션클립은 재생 중 시각 중심이 이동하므로, 수명만 늘려 재면 오독한다 — `msw-asset-verify` §"고른 뒤" 참조).

**자산을 바꾸면 이 값도 다시 재야 한다.** 재는 방법은 광맥 셀에 그대로 얹어 보고 화면에서 밀린 방향·양을 보는 것이다.
