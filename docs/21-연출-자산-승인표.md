## 1. 광맥 — 핵심 발견

검색 결과 **광맥 stage 표현에 그대로 쓸 수 있는 자산 2개**를 찾았다. 둘은 역할이 달라 **함께 쓰는 것**을 권한다.

> ⚠️ **2026-07-31 육안 검증으로 정정.** `condition1~5`는 **깔끔한 5단계 잔량 램프가 아니다.** 실제로는 **청록 결정 5종(크기 차이) + `condition2` 하나만 빨강 색상 변종**이다. 따라서 `condition2`는 잔량 램프에서 빼야 하고, 남는 청록 5종에서 4개를 고른다. 근거는 §6.2.

**관측된 잔량 순서** (많은 것 → 적은 것, §6.2 스크린샷 기준):

```
stand ≈ condition1  >  condition3 ≈ condition4  >  condition5
```

**확정 매핑** (2026-07-31 오너 승인 · D8 **C206**)

| `ReserveStage` | 의미 | 자산 | RUID |
|:-:|---|---|---|
| 3 | 만재 | `condition1` | `0f44530d655f4e33bfbe43423450ee9f` |
| 2 | — | `stand` | `a0bd28cbdcd54445827f0375f24266b5` |
| 1 | — | `condition4` | `2daf76debab042e09b2d3bf2d5ba575f` |
| 0 | 고갈 | `condition5` | `40c805ead61d440889632ef2244dab30` |

- `condition3`은 `condition4`와 거의 같은 크기라 미사용으로 남긴다. 관측상 `condition3` > `condition4`이므로 낮은 stage에는 더 작은 `condition4`를 두는 쪽이 내림차순에 맞는다.
- **5단계(청록 5장 전부 사용)는 채택하지 않았다.** `VeinTickSimulator.MaxReserveStage`를 3→4로 올려야 하는데, 광맥당 채굴 3→4회(**+33%**)·완전 회복 15→20틱으로 경제 밸런스가 바뀐다. **`MaxReserveStage = 3`(stage 0~3, 4단계) 유지**가 확정이다 (C206).
- **`stand`과 `condition1`의 차이가 작다**(둘 다 큰 결정 + 위성 파편 2개). stage 3↔2 구분이 약하므로, 구분이 부족하면 stage 3에만 `Scale` 미세 증가나 밝기 보정을 얹는 것을 검토한다.
- **`condition2`(빨강)는 잔량 표현에 쓰지 않는다.** 색만 다르고 형태는 같아 D5 §8 **V1**("색 외의 형태로 구분")을 위반한다. 특별 광맥 후보로도 같은 이유로 부적합하다. 희귀 광맥 강조 같은 다른 용도의 후보로만 남긴다.

### 1.3 광물 3종(돌·철·금) 구분 방법 — 결정 필요

위 두 자산은 **광물 종류 구분이 없다.** Q1-ⓐ를 문자 그대로 지키려면 `oreType × stage` **12개 서로 다른 스프라이트**가 필요한데, 그런 자산군은 검색으로 찾지 못했다.

| 방안 | 내용 | 평가 |
|---|---|---|
| A | `부유석` condition 4개를 stage로 쓰고, **광물 종류는 `SpriteRendererComponent.Color` 색조로 구분** | 자산 제작 0. 단 광물 종류가 **색으로만** 구분돼 D5 §8 **V1**("색 외의 형태로 구분")을 광물 축에서 어긴다 |
| B | `msw-painter`로 **12개를 직접 제작** | V1을 완전히 충족. 픽셀아트 12장 제작 비용 |
| **C ✅ 확정** | stage는 `부유석` condition, **광물 종류는 광맥 위에 작은 아이콘 뱃지**를 겹쳐 표시 | 자산 제작 0이면서 종류가 **형태로** 구분된다 |

**C로 확정 (2026-07-30, D8 C205).** D5 §3이 일반 광맥의 표현을 "돌/철/금의 형태·색·**작은 아이콘** + stage 0~3 크기·균열·광택 변화"로 규정하고 있어, 아이콘 뱃지는 기획 원문에 이미 들어 있는 방식이다. 승인된 아이콘(`docs/20` §0)을 그대로 재사용하므로 추가 검색도 필요 없다.

**구현 형태**

- 광맥 엔티티 = 부모(`SpriteRendererComponent` = `부유석` condition, stage에 따라 교체) + **자식 뱃지 엔티티**(`SpriteRendererComponent` = `docs/20` §0의 광물 아이콘).
- 뱃지는 광맥 스프라이트의 **상단**에 작게 얹는다. 크기는 원본 아이콘(28~32px)을 월드 단위로 환산해 약 0.3 unit 내외.
  - **구현 확정 (2026-08-04)**: 부모 로컬 `(0, 0.62)`(일반) / `(0, 0.45)`(특별), `Scale` 1.4. 화면에서는 광맥의 **우상단**에 붙는다 — 부모 자식 좌표에 스프라이트 pivot 이 곱해진 결과다. 광맥을 가리지 않고 종류 식별도 되므로 이 위치로 확정했다. 작성 당시의 "좌상단 또는 상단 중앙"은 실측 전 표현이었다.
- 뱃지는 `oreType`으로만 결정되고 **stage에 따라 바뀌지 않는다.** stage 변화는 부모 스프라이트가 담당한다.
- 뱃지의 `SortingLayer`·`OrderInLayer`를 부모보다 **위**로 둔다. 같은 값이면 가려질 수 있다.
- 고갈(stage 0)에서도 뱃지는 유지한다 — "여기가 무슨 광맥이었는지"를 알아야 플레이어가 회복을 기다릴 수 있다.

|---|---|
| `cap` | **광부 정체성을 혼자 다 짊어진다.** 노란 안전모가 원경에서도 가장 먼저 읽히는 단서다 |
| `coat` | 흰 상의 + 멜빵끈이 또렷하다. 안전모의 노랑과 대비돼 상하가 구분된다 |
| `pants` | 렌더 자체는 정상. 다만 **무릎 위에서 끊기는 짧은 청색 하의**로 보여 "청바지"라는 이름과 실루엣이 다르다. 원본 크기에서는 얇은 하늘색 띠 정도로만 읽힌다 → **오너 판단 필요.** 작업복 느낌을 더 주려면 대체 후보 `데님 카고 바지`가 낫다 |
| `weapon` | 금색 곡괭이가 몸을 가로질러 또렷하게 잡힌다. `ShowDefaultWeaponEffects` 기본값 `true` 때문에 **상시 반짝임**이 함께 붙는다 — 대기 중인 일꾼이 계속 반짝이므로, 채굴 먼지(§5)와 신호가 겹친다고 판단되면 `false`로 끈다 |

**구현 시 걸린 것 2가지** (다음에 다시 만나지 않도록)

- **`UseCustomEquipOnly = true` 가 필수다.** 끄면 접속 계정의 기본 코스튬이 먼저 깔리고 그 위에 커스텀이 얹혀 광부 외형이 계정마다 달라진다. 일꾼은 플레이어가 아니므로 항상 켠다.
- **`head` 는 슬롯이 없다.** `Custom*Equip` 17종에 `CustomHeadEquip`이 없고, 엔진이 `body` 색에 맞춰 자동 처리한다. §7.1의 `head` RUID는 **대입할 곳이 없는 참고값**이다. `CustomFaceEquip`을 비워 둬도 얼굴은 정상 렌더된다(실측 확인).

**기본 아바타** (`getAvatarDefaults`) — `body` `3cf4cb29ae344577b9eed37e531688a4` / `head` `5069d11260b549869339cd46777306f9`

> **`head`는 검색 대상이 아니다.** 아바타 슬롯 목록에 `head`가 없기 때문이다 — 옷·장식 슬롯은 `cap`/`hair`/`face`/`faceaccessory`/`coat`/`pants`/`shoes`/`weapon` 등이고, `body`와 `head`는 **캐릭터의 기본 신체 부위**라 `getAvatarDefaults`가 주는 값을 그대로 쓴다. 검색해도 안 나오는 것이 정상이며, 위 RUID를 쓰면 된다. 얼굴·머리 생김새를 바꾸고 싶으면 `hair`(머리카락) / `face`(얼굴) 슬롯을 별도로 검색한다 — 이번 범위 밖이며 T-06(외형) 과제다.

- `cap`은 이름이 직접 "안전제일 모자"라 광부 정체성이 가장 명확하다. 영문 `Hard Hat`도 같은 계열이다.
- `coat`(멜빵)만으로는 하의가 비어 기본 바지가 노출되므로 `pants`를 함께 지정한다. 작업복 느낌을 더 주려면 `데님 카고 바지`가 대안이다.
- `weapon`의 곡괭이 2종은 **재질만 다르다**. 일꾼 등급·수레 강화 단계에 따라 `황금 → 다이아`로 바꾸면 성장감을 줄 수 있다(T-06 범위).
- 아바타 아이템 RUID는 `CostumeManagerComponent`의 `Custom*Equip` 슬롯에 넣는다. 슬롯 매핑은 `msw-avatar` 스킬을 따른다. **인벤토리·UI에 아이콘으로 그릴 때만 `thumbnail://` 접두어**가 필요하고, 착용에는 붙이지 않는다.

**T-06(외형·도감·가챠)과 겹친다.** 이 티켓에서는 **기본 외형만** 지정하고, 피스 수집·장착 시스템은 T-06에 남긴다. 아바타 슬롯 매핑과 애니메이션 파이프라인은 `msw-avatar` 스킬 문서를 따른다.

> **미검색.** T-04 착수 시 `searchAvatarItems`로 위 3슬롯을 찾는다. 기본 아바타 RUID는 `getAvatarDefaults`로 얻는다.

- **일반 광맥 = `부유석`.** "광맥다움"은 `신비한 광석`이 낫지만, **Q1이 요구한 stage 4단계를 만들 수 있는 자산은 `부유석`뿐**이다. 이 제약이 미관보다 우선한다.

- **특별 광맥 = `신비한 광석`.** 바위 받침이라는 **형태 차이**로 구분되므로 D5 §8 **V1**을 충족한다(`condition2` 빨강은 색만 달라 V1 위반이라 부적합). 게다가 §1.2대로 `hit1`/`regen`/`die1`/`_audio/Damage`를 같은 자산군에서 가져오므로 연출 일관성도 얻는다.

### 7.2 Depot · 링 육안 확인 (2026-07-31)

Depot 후보 6개와 링 후보 4개를 `farm01`에 native scale로 배치해 스크린샷으로 판정했다(작업 스크립트: `.builder-work/place_fx_asset_probe.cjs`). 검증 후 전량 제거하고 맵은 커밋 상태로 복원했다.

- Depot 후보에는 **나무 상자 더미·열린 궤짝·큰 나무 상자·광석 실은 광차·천 덮인 광차·금속 벤치**가 있었다. 계약 원문이 "목재 상자/**광차**"이므로 광차를 1순위로 뒀다.
- 링 후보 4개 중 **실제로 링 형태인 것은 2개**뿐이고, 나머지는 속이 찬 갈색 원(그림자용)과 별 반짝임이었다. 검색 이름만 봤다면 걸러낼 수 없었다.
