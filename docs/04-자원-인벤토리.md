## 1. 범위

- 포함: 광물 종류, 채굴·운반·저장 흐름의 상태 전이, 수레 용량 규칙, 창고 저장, HUD/인벤토리 표시 항목, 저장 정책, 튜닝 상수표
- D2에서 스텁으로 예약해 둔 `mine`/`load`/`unload` 액션과 `cart_full`/`cart_empty` 조건을 **이 문서에서 실동작으로 확정**한다.
- 제외: 광물 판매·상점·화폐(차기), 다중 일꾼(D4).

## 2. 자원 흐름 (한눈에)

광물은 **광맥 → 일꾼 손 → 수레 → 창고** 순서로 4개의 저장 위치를 거친다. 각 위치의 용량과 "틱마다 자동 회복" 여부는 아래 표에서 서로 다르니 혼동하지 말 것.

| 순서 | 저장 위치 | 코드 | 용량 | **틱마다 +1 자동 회복?** | 이 위치로 들여오는 액션 |
|:--:|---|---|:--:|:--:|---|
| 1 | 광맥(셀) | `VeinState[x,y].stage` | 0~3 (`MaxReserveStage`) | **O** — `RecoverTick`마다 +1 (여기만 회복됨) | (자연 회복) |
| 2 | 일꾼 손 | `pending` | 1 (`HandCapacity`) | X | `mine` (채굴) |
| 3 | 수레 | `cart.count` | 20 (`CartCapacity`) | X | `load` (싣기) |
| 4 | 창고 | `Depot[ore]` | 무제한 | X | `unload` (내리기) |

> **핵심**: "틱마다 +1 회복"은 **1번 광맥에서만** 일어난다. 손·수레·창고는 액션으로만 채워지고 자동 회복이 없다. 채굴하면 광맥 stage가 −1 되고, 시간이 지나면 다시 +1씩 차오른다(방치형 누적 성장).

핵심 순환: **채굴 → 싣기 → (수레 만재) → 창고로 이동 → 내리기 → 다시 채굴**. 이 순환을 반복·조건 블록으로 짜는 것이 게임의 목표. 예) `R∞[ IF광물[M, L], IF(cart_full)[ (창고로 이동), U ] ]`.

## 3. 광물 종류

시작은 **1종("돌", Stone)**으로 구현하고, 구조만 다종 확장 가능하게 둔다. 다종은 ⑤단계 이후.

| ID | 이름 | 희귀도 | 셀당 회복 틱(ReserveStage +1 주기) | 채굴 1회 획득량 | 비고 |
|---|---|:--:|:--:|:--:|---|
| `stone` | 돌 | common | 5틱 | 1 | 시작 광물. 값 조정 대상 |
| `iron` | 철 | uncommon | 10틱 | 1 | 구조 검증용 예약(미배치 가능) |
| `gold` | 금 | rare | 20틱 | 1 | 예약 |

- **셀-광물 매핑**: 각 광맥 셀은 `oreType` 하나를 가진다(맵 배치 시 결정). 현재 `VeinState["x,y"] = { ore = "stone", stage = N }` 구조 재활용.
- 회복은 D2/기존 틱 시뮬레이터가 담당: `stage < 3`이면 `RecoverTick`마다 +1. 채굴 시 `stage`를 1 감소(고갈=0). *(기존 코드는 stage를 3까지 올리기만 했으므로, 채굴로 인한 감소 경로를 추가)*

## 4. 상태 전이 상세 (액션별 확정 동작)

| 액션 | 선행 조건 | 성공 시 | 실패 시(틱은 소비) |
|---|---|---|---|
| `mine` | 현재 셀 `stage ≥ 1` **그리고** 일꾼 손 비어 있음 | 셀 `stage -= 1`, 일꾼 손 = 광물 1 (ore=셀의 oreType) | 손이 이미 차 있으면 `[Worker] hand full`; 광맥 고갈이면 `[Worker] vein empty` |
| `load` | 일꾼 손에 광물 있음 **그리고** 수레 여유(`cart.count < CartCapacity`) | 수레 count += 1, 손 비움 | 손 비었으면 `hand empty`; 수레 가득이면 `cart full` |
| `unload` | 현재 셀이 창고(Depot) **그리고** 수레 count > 0 | 창고 누적 += 수레 count, 수레 비움 | 창고 아니면 `not at depot`; 수레 비었으면 `cart empty` |

- **손(pending) 슬롯**: 용량 1. mine과 load를 분리한 이유 — "캐서 바로 수레에 싣기"를 두 블록으로 표현해 알고리즘적 사고를 유도. (원한다면 v2에서 `mine`이 자동 load하는 간이 모드 옵션 추가 가능 — 튜닝 상수 `AutoLoadOnMine`)
- **조건 연동**: `cart_full` = `cart.count >= CartCapacity`, `cart_empty` = `cart.count == 0`. D2에서 스텁이던 두 조건이 여기서 실값이 된다.

## 5. 창고(Depot)

- 맵에 **고정 셀 1개**로 배치(시작). 좌표는 맵 배치 시 결정한다. 현재 구현은 좌표 중복을 피하기 위해 맵 범위 원장인 `VeinTickSimulator`가 `DepotCellX/Y`를 보유하고, `WorkerController`는 `IsDepot` API만 호출한다.
- 누적 저장량은 **무제한**(방치형 성장 지표). 서버가 단일 원장으로 보유: `Depot["stone"] = 총량`.
- 저장량 변경 시 서버→클라 통지 → HUD 갱신(§6 표시 항목). 통지 방식(이벤트/@Sync property)은 프로그래머 재량, 단 **원장은 서버 소유**.

## 6. UI — HUD & 인벤토리 창

### HUD (상시 표시, 화면 상단)
| 항목 | 표시 | 갱신 시점 |
|---|---|---|
| 창고 보유 광물 | 아이콘 + 수량 (다종이면 주요 1~3종) | 저장량 변경 시 |
| 수레 적재 | `12 / 20` 형태 | load/unload 시 |

### 인벤토리 창 (버튼으로 토글)
- 광물별 수량 목록(1종이면 1행). 스크롤은 다종 확장 시 필요.
- `.ui`는 UIBuilder 경유 신규 그룹으로 작성(기존 `ui/` 폴더). HUD는 별도 UIGroup, 인벤토리 창은 팝업 UIGroup으로 분리.
- **③단계 미완이어도 HUD 골격은 먼저 배치 가능** — 값은 0으로 초기화.

## 7. 저장 정책

| 옵션 | 내용 | 권장 |
|---|---|---|
| 세션 내 유지 | Play 세션 동안만 창고 누적 보존, 종료 시 리셋 | **④단계 기본** — 구현 단순, 대회 시연엔 충분 |
| DataStorage 영구 저장 | `_DataStorageService`로 유저별 누적 영구 보존 | ⑤단계 이후 확장. 방치형 정체성엔 궁극적으로 필요하나 지금은 과투자 |

→ ④단계는 **세션 내 유지**로 구현하고, 원장 접근을 함수로 감싸(`AddToDepot`/`GetDepot`) 나중에 DataStorage로 교체 시 그 함수만 바꾸면 되도록 설계.

## 8. 튜닝 상수표 (한 곳에 모아 노출 — 프로그래머 필수)

| 상수 | 시작값 | 의미 |
|---|:--:|---|
| `TickInterval` | 0.4s | 틱 주기(기존값 유지) |
| `RecoverTick.stone` | 5틱 | 돌 광맥 stage +1 주기 |
| `MaxReserveStage` | 3 | 광맥 최대 매장 단계 |
| `MineYield` | 1 | 채굴 1회 획득량 |
| `CartCapacity` | 20 | 수레 최대 적재 |
| `HandCapacity` | 1 | 일꾼 손 슬롯(고정 권장) |
| `AutoLoadOnMine` | false | true면 mine이 자동 load(간이 모드) |

## 10. D4 연동 상태

- D4-A에서 수레·손·프로그램을 `WorkerController` 인스턴스별로 유지하고, 창고는 맵의 `VeinTickSimulator` 공용 원장으로 연결했다.
- `MineInventoryController`는 `BlockProgramController`의 선택 대상과 같은 일꾼을 표시하므로 프로그램 전송 대상과 HUD 수치가 어긋나지 않는다.
