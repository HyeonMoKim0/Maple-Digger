# D9. 메이플 디거 — 밸런스 검증

> 작성일: 2026-07-31
> 상태: **✅ 검증 완료 · 권고 1·2·5 반영 (2026-07-31, D8 C207)** — 경제 수치는 조정하지 않는다. 남은 권고 3·4는 구현 시, 6은 미결.
> 목적: D7 §5.3의 초기 경제 수치가 **실제로 의도한 진행 속도를 만드는지** 계산으로 검증한다.
> 근거 도구: `tools/balance_sim.cjs` — 코드 상수를 그대로 옮겨 틱 루프를 재현하는 시뮬레이터. **결론이 의심되면 이 스크립트를 다시 돌린다.**
> 선행 문서: D7 §4·§5(수치), F7-B §2·§3·§5(판매·해금·강화), F6(맵 레이아웃)

## 0. 왜 이 문서가 필요했나

D7 §10.2 **P4**가 "깊은 광산을 **10~15분 내** 해금"을 유일한 진행 목표로 두고 있는데, **그 값이 실제로 달성되는지 확인한 기록이 없었다.** §5.3도 "첫 Play 테스트 값"이라고만 적혀 있다.

이 공백은 실제 작업을 막았다. 2026-07-31 광맥 stage를 4단계에서 5단계로 늘릴지 검토할 때, "채굴량이 33% 늘어난다"까지는 계산했지만 **그것이 허용 범위인지 판정할 기준이 없어** 오너 판단으로 넘겼다(C206). T-02 맵 강화는 효과 4종을 한꺼번에 추가하므로 같은 상황이 더 크게 반복된다.

## 1. 검증 방법

### 1.1 시뮬레이터가 재현하는 것

`tools/balance_sim.cjs`는 `VeinTickSimulator`의 틱 계약을 그대로 옮겼다.

```
매 틱:  AdvanceTick(모든 광맥 회복 1스텝) → AdvanceWorkers(일꾼당 액션 1개)
회복:   recoverElapsed += 1
        recoverElapsed >= recoverTicks 이면 리셋하고 stage +1 (stage < MaxReserveStage 일 때만)
채굴:   stage >= 1 이고 손이 비었으면 stage -1, 손에 광물 1개
싣기:   손 → 수레 (별도 액션. AutoLoadOnMine = false)
하역:   창고 셀에서 수레 전량을 1틱에 비운다
이동:   4방향, 1셀 1틱
```

맵 레이아웃(광맥 좌표·광물 종류·`recoverTicks`)은 **`.map` 파일에서 직접 읽는다.** 하드코딩하지 않으므로 맵을 고치면 결과가 따라 바뀐다.

### 1.2 검증에 쓴 상수 — 전부 코드 실측

| 상수 | 값 | 출처 |
|---|---:|---|
| `TickInterval` | 0.4초 | `VeinTickSimulator` |
| `MaxReserveStage` | 3 | 〃 (stage 0~3, 채굴 가능 3회) |
| `StoneRecoverTicks` | 5 | 〃 (광맥당 5틱에 1단계) |
| `CartCapacity` | 20 | 〃 · `AccountProfileService` |
| `HandCapacity` / `MineYield` | 1 / 1 | 〃 |
| `AutoLoadOnMine` | false | 〃 (**채굴과 싣기가 별도 액션**) |
| 판매 단가 돌 / 철 / 금 | 1 / 5 / 20 골드 | `EconomyService` |
| `TokenOreThreshold` | 20 | 〃 (대표 광물 20개 판매당 토큰 1개) |
| 깊은 광산 해금 | 골드 180 · 토큰 6 · 돌 120 | `ProgressionService` |
| 보석 광산 해금 | 골드 700 · 토큰 10 · 돌 200 · 철 60 | 〃 |

**구현이 D7 §5.3 제안값과 정확히 일치한다.** 문서와 코드가 어긋난 곳은 없었다.

### 1.3 기준 프로그램 2종

플레이어 숙련도에 따라 처리량이 크게 갈리므로 양 끝을 잡았다.

| 이름 | 내용 | 대표하는 플레이어 |
|---|---|---|
| **P1 왕복** | 가장 가까운 광맥 1개만 왕복 (`이동 → 채굴 → 싣기 → 이동 → 하역`) | 튜토리얼만 마친 상태. 반복·조건 블록 미사용 |
| **P2 순회** | 광맥을 순회하며 각 광맥에서 3회 채굴, 수레가 차면 하역 | 반복 블록을 이해하고 수레 용량을 활용 |

## 2. 광맥 공급 상한 — 일꾼 수와 무관한 천장

**가장 중요한 구조적 사실이다.** 광맥은 `recoverTicks`마다 1단계씩만 회복하므로, 맵이 공급할 수 있는 광물의 양에는 **일꾼 수와 무관한 물리적 상한**이 있다.

```
맵 공급 상한 = Σ(광맥별 1 / recoverTicks) [ore/틱] ÷ 0.4 × 60 [ore/분]
```

| 광산 | 광맥 | 공급 상한 |
|---|---:|---|
| 초보 (`beginner_mine`) | 4 | 돌 **120/분** |
| 깊은 (`deep_mine`) | 7 | 돌 90/분 · 철 **120/분** |
| 보석 (`gem_mine`) | 11 | 돌 90/분 · 철 120/분 · 금 **120/분** |

일꾼 1명의 이론 최대는 **75/분**이다(채굴+싣기 2틱, 이동·하역 0 가정). 따라서 **초보 광산은 일꾼 2명이면 공급 상한의 절반을 넘고, 4명이면 천장에 닿는다.**

## 3. 처리량 실측

30분(4,500틱) 시뮬레이션 결과. 단위는 분당 개수.

### 3.1 초보 광산

| 일꾼 | P1 왕복 | P2 순회 | 배수 |
|:-:|---:|---:|---:|
| 1 | 30 | **54** | 1.8× |
| 2 | 29 | 85 | 2.9× |
| 3 | 29 | 100 | 3.4× |
| 4 | 29 | **119** | 4.1× |
| 5 | 29 | 119 | 4.1× |

**두 가지가 드러난다.**

1. **P1은 일꾼을 늘려도 30/분에서 고정된다.** 시작점이 창고 주변에 몰려 있어(`(0,0) (0,1) (-1,0) (-1,1) (-2,0)`) 모든 일꾼이 같은 광맥 `(1,0)`을 고르고, 그 광맥 하나의 회복 속도(0.2 ore/틱 = 30/분)가 그대로 천장이 된다. **반복 블록을 배우지 못한 플레이어는 일꾼을 사도 채굴량이 전혀 늘지 않는다.**
2. **P2는 4명에서 공급 상한 120에 닿고, 5번째 일꾼은 무의미하다**(119 → 119).

### 3.2 깊은 광산 · 보석 광산

전 광맥을 순회(P2)하면 광물이 섞여 나와 종류별 속도가 낮아진다. **광물별로 일꾼을 전담시키는 쪽이 훨씬 빠르다.**

| 배정 | 결과 (일꾼 3명) |
|---|---|
| 깊은 · 전 광맥 순회 | 돌 36/분 · 철 54/분 |
| 깊은 · **철 전담** | 철 **77/분** |
| 깊은 · **돌 전담** | 돌 **88/분** |
| 보석 · 전 광맥 순회 | 돌 21/분 · 철 33/분 · 금 33/분 |
| 보석 · **금 전담** | 금 **66/분** |

금이 철보다 느린 것은 광맥이 창고에서 멀기 때문이다(금 광맥 `x = 12~16`, 철 `x = 6~9`).

## 4. 해금 요건 → 소요 시간

### 4.1 깊은 광산 (D7 P4 목표: 10~15분)

필요: **골드 180 + 토큰 6 + 돌 120 납품**

- 토큰 6 = 돌 120개 판매 (20개당 1)
- 골드 180 = 돌 180개 판매 (1골드/개) → 토큰 9개가 따라온다
- **골드가 제약**이므로 필요한 총 채굴량 = 180(판매) + 120(납품) = **돌 300개**

| 경로 | 채굴 시간 |
|---|---:|
| P1 왕복 · 일꾼 1명 (30/분) | **10.0분** |
| P2 순회 · 일꾼 1명 (54/분) | **5.6분** |
| P2 순회 · 일꾼 2명 (85/분) | 3.5분 |

### 4.2 보석 광산

필요: **골드 700 + 토큰 10 + 돌 200 + 철 60 납품**

철이 5골드라 **철을 파는 쪽이 압도적으로 효율적**이다.

| 전략 | 판매 | 총 채굴량 |
|---|---|---|
| A · 철만 판매 | 철 200개 → 1,000골드 + 토큰 10 | 철 260 + 돌 200 |
| B · 철 140 + 돌 60 판매 | 700골드 + 토큰 10 | 철 200 + 돌 260 |

일꾼 3명 순회(돌 36 / 철 54)로 계산하면 **A는 5.6분**(돌 200 ÷ 36), **B는 7.2분**(돌 260 ÷ 36)이다. 둘 다 돌이 병목이다 — **철 광맥이 돌보다 많아서**(4 vs 3) 생기는 역전이다.

## 5. 판정

### 5.1 P4 목표는 "무엇을 재는지"가 정의돼 있지 않다 ★

순수 채굴 시간은 **5.6분(숙련) ~ 10.0분(초보)** 이다. 목표 하한 10분에 닿는 것은 **P1 왕복뿐**이고, 반복 블록을 쓰는 순간 목표의 **절반**이 된다.

이 차이는 수치 문제가 아니라 **정의 문제**다. "10~15분"이 무엇을 포함하는지가 D7에 없다.

| 해석 | 판정 |
|---|---|
| ⓐ 순수 채굴 시간 | **미달** — 숙련 플레이 5.6분으로 목표의 56% |
| ⓑ 튜토리얼 + 프로그램 작성 + UI 조작 포함한 **첫 접속 총 경과 시간** | **타당** — 튜토리얼 8단계와 블록 조립에 수 분이 들어간다 |

> **✅ 2026-07-31 오너 확정 — ⓑ로 간다 (D8 C207).** D7 §5.3과 §10.2 P4의 원문도 이에 맞춰 고쳤고, C149에 의미를 달았다. **경제 수치는 조정하지 않는다.**

이유는 세 가지다.

1. 순수 채굴 시간을 목표로 삼으면 **숙련 플레이어를 벌주는 밸런싱**이 된다. 반복 블록을 배우는 것이 이 게임의 핵심 학습인데, 잘 배울수록 목표에서 멀어진다.
2. C204가 "두 번째 일꾼 5분" 시간 목표를 폐기하면서 **시간 기준을 비용 기준으로 옮기는 방향**을 이미 잡았다. P4도 같은 방향이 일관된다.
3. ⓑ라면 현재 수치는 **조정 불필요**하다. 채굴 5.6~10분 + 튜토리얼·조립 4~6분 ≈ 10~15분으로 목표에 들어온다.

### 5.2 P1 플레이어는 일꾼을 사도 채굴량이 늘지 않는다 ★ — **해소됨 (2026-08-14, T-11)**

> **T-11 이 근본 원인을 없앴다.** 시작 셀을 광맥별로 분산해 이제 5명 전부가 **각기 다른 광맥 앞**에서 시작한다(초보 광산은 광맥이 4개라 4명 + 창고 공유 1명). Play 실측으로 일꾼 1의 프로그램을 그대로 복사한 일꾼 2가 **같은 틱에 다른 광맥을 캤다**(`mined cell 1,0` + `mined cell 2,0`). 배치와 근거는 `docs/18` T-11, 검수는 `docs/16` §25.
>
> 아래 30→29→29→29 수치는 **분산 이전의 측정값**이다. `tools/balance_sim.cjs` 는 시작 셀을 스크립트 상단 `STARTS` 상수로 들고 있으므로, 재측정하려면 그 값을 새 배치로 맞춰야 한다.

§3.1의 30 → 29 → 29 → 29다. **일꾼 2를 60골드에 사고도 체감이 0인 구간이 존재한다.**

튜토리얼 8단계가 일꾼 구매를 가르치는데(F7-E §4), 그 직후 플레이어가 얻는 것이 **아무것도 없다.** 튜토리얼이 반복 블록(5단계)을 먼저 가르치므로 이론상 P2로 넘어가 있어야 하지만, 배운 것을 **두 번째 일꾼에게 적용하는 법**은 가르치지 않는다.

**권고 (구현 판단, 밸런스 수치 변경 아님)**

- 일꾼별 시작점이 다르므로 **같은 프로그램을 복사하면 광맥에 닿지 못한다.** F7-C 프로그램 라이브러리(T-05)가 "복사 후 대상 확인"을 요구하는 이유가 여기 있다. 이 경고를 **일꾼 2 구매 직후에 반드시 노출**한다.
- 또는 초보 광산의 일꾼 시작점을 광맥 쪽으로 분산해 naive 복사도 최소한 동작하게 한다. **단 이건 F6 레이아웃 변경이라 별도 결정이 필요하다.**

### 5.3 5번째 일꾼은 초보 광산에서 효과가 없다

공급 상한 120/분에 4명(119)이면 이미 닿는다. 일꾼 5는 **1,600골드 + 돌 300 + 철 120 + 금 30**인데 초보 광산에서는 증가분이 0이다.

이건 결함이 아니다 — 일꾼 5는 보석 광산(공급 상한 330/분)용이다. 다만 **구매 화면에서 "현재 광산에서는 효과가 제한적"임을 알려주지 않으면** 플레이어가 손해로 느낀다.

### 5.4 `MaxReserveStage`를 4로 올렸을 때 (C206에서 보류한 검토)

광맥당 채굴 3회 → 4회가 되지만, **공급 상한은 바뀌지 않는다.** 상한은 `1/recoverTicks`로 결정되고 `MaxReserveStage`는 "한 번에 쌓아둘 수 있는 최대치"일 뿐이다.

바뀌는 것은 **초반 버스트**다. 세션 시작 시 광맥이 만재이므로 초기 재고가 12개 → 16개가 되고, 일꾼이 광맥을 순회하는 동안 고갈될 확률이 낮아져 **P2 처리량이 실질 상승**한다. 반대로 P1은 거의 영향이 없다.

**결론: C206의 4단계 유지 판단은 타당하다.** 5단계는 숙련 플레이어(P2)만 이득을 보므로 §5.1의 격차를 더 벌린다.

## 7. T-02(맵 강화) 착수 시 이 문서를 쓰는 법

맵 강화 효과 4종 중 **`recovery`만 공급 상한을 올린다.**

| 효과 | 공급 상한 | 처리량 |
|---|---|---|
| `recovery` (회복 속도) | **오른다** — `recoverTicks`가 실질 감소 | 상한에 걸려 있을 때만 유효 |
| `yield` (획득량) | 안 오름 | 같은 채굴 횟수로 더 많이 얻으므로 **직접 상승** |
| `rareChance` | 무관 | 희귀 광물만 |
| `specialSpawn` | 무관 | 특별 광맥 주기만 |

따라서 **초보 광산 주 효과가 `yield`인 것은 타당하다** — 일꾼 1~2명 구간에서는 공급 상한에 여유가 있어 `recovery`를 올려도 체감이 없기 때문이다. 반대로 **깊은 광산 주 효과가 `recovery`인 것도 타당하다** — 일꾼이 3명 이상으로 늘어난 시점이라 상한이 실제 제약이 된다.

T-02 구현 후에는 **`tools/balance_sim.cjs`에 보너스 배율을 넣어 다시 돌린다.** 회복 배율은 `AdvanceTick`의 `recoverElapsed += multiplier` 한 줄에 대응한다.

## 8. 재현 방법

```bash
node tools/balance_sim.cjs
```

맵 레이아웃은 `.map`에서 읽으므로 별도 갱신이 필요 없다. 코드 상수(`MaxReserveStage`·`StoneRecoverTicks`·`CartCapacity`·판매 단가)를 바꿨다면 스크립트 상단의 상수도 함께 맞춘 뒤 돌린다.

> **한계.** 이 시뮬레이터는 **서버 시뮬레이션의 산술만** 재현한다. 실제 Play에서의 UI 조작 시간, 프로그램 조립 시간, 플레이어의 시행착오는 포함하지 않는다. §5.1의 ⓑ 해석을 검증하려면 **사람이 새 계정으로 첫 접속부터 깊은 광산 해금까지 실측**해야 하며, 이는 `docs/16`의 사용자 검수 항목이다.

### 8.2 판정

1. **P1(단일 광맥 왕복)은 손 용량과 무관하게 30/분에 묶인다** — 병목이 왕복 시간이 아니라 **광맥 회복 속도**(rt=5틱, 광맥당 30/분)이기 때문이다. 손 3개는 왕복 횟수를 줄일 뿐 단일 광맥의 공급 상한을 못 넘는다.
2. **P2(전 광맥 순회)가 극적으로 좋아졌다** — 이어 캐기로 광맥당 3개를 받아 나오므로 순회 1바퀴의 수확이 3배다. 초보 광산 1명 70/분(구 측정 대비 대폭 상승), 3명이면 사실상 천장(116/120).
3. **해금 소요 시간은 §4의 추정보다 크게 단축된다** — P2를 아는 플레이어 기준. P1만 아는 초보는 여전히 30/분이므로, 튜토리얼이 가르치는 왕복 프로그램과 실제 최적 플레이의 격차가 커졌다. 격차를 줄일지(광맥 회복 하향 등)는 오너 판단 대상.
4. §5.3의 "5번째 일꾼 무효" 판정은 P2 기준 4명부터 천장 포화(119/분)로 형태가 바뀌었다 — 결론(초보 광산에서 4~5번째 일꾼의 한계 효용 없음)은 유지된다.
