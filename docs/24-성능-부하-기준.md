## 1. 목적·범위

- **범위**: PC 1920×1080 · 1인 세션 (MVP 확정 기준, As-built). 모바일(T-09)·멀티 유저는 보류 티켓 범위라 이 문서의 판정선에 포함하지 않는다.
- **판정선의 용도**: ① C212 조건 ③의 통과/미달 판정 ② 이후 기능 추가 시 같은 절차 재측정으로 **성능 회귀 감지**.
- ⚠️ **절대치의 한계**: 측정은 Maker Play(에디터 시뮬레이션 — 서버·클라가 한 프로세스)에서 했다. 실서버·실클라의 절대 수치와 다르므로, 판정선은 "같은 환경에서 재측정했을 때"의 기준이다. 실기기 최종 확인은 §7.

## 3. 부하 모델 (worst case 정의)

- **시뮬레이터 3개 병렬**: 세 광산 맵의 `VeinTickSimulator` 는 플레이어 위치와 무관하게 **서버에서 전부 동시에** 돈다 (실측: farm01·deep_mine·gem_mine 각각 정확히 2.5틱/s). 서버 부하 모델은 항상 "3심 + 등록 일꾼"이다.
- **S1 현실형 최대**: 일꾼 5명 전원이 기본왕복 무한 프로그램(`repeat inf { E, mine, load, W, unload }`) 실행 — 틱당 5액션 + 채굴 먼지·선택 링·marker 갱신·cue 재생이 최대 빈도로 발생. (일꾼 2~5는 복사 프로그램으로 하역 불가 상태(수레 가득)를 포함 — T-11 문서화된 실사용 상황 그대로)
- **S2 합법 최악(인터프리터)**: 일꾼 5명 × 30블록(상한) 프로그램 — `repeat inf { (if cart_full{W})×14, mine }`, 틱당 조건 평가 ~15회로 `MaxEvaluationsPerTick=20` 에 근접. 검증기가 통과시키는 가장 무거운 축.

| 런타임 Error/Warning | 0 | 0 | 0 |

- **틱 예산**: 최악 부하에서도 틱 레이트 편차 ±0.3% — 0.4초 틱 예산은 5명 × 3맵에서 여유가 크다.
- **프레임 스파이크는 부하 지속이 아니라 전환 순간에만** 났다 (프로그램 5개 일괄 기동, 프로브 기동). 지속 구간에서는 100ms 초과 0건.
- **로그량이 실질적 병목이다**: 부하 중 콘솔 로그 **분당 ~1,300건** (`[Worker N]` 5명 각 ~150/분 + `[WorkerFx]` + `[MineSound]` + `[VeinTick]`). 프레임에는 영향이 관측되지 않았으나 콘솔 진단성을 크게 해친다 — §5 권고 참조.
- **DataStorage**: 부하와 무관하게 이벤트 시(구매·설정 디바운스·종료 저장)에만 호출 — 루프 내 호출 없음 재확인.

## 5. 판정선 — C212 조건 ③

§6 절차로 재측정했을 때 아래 **5개 전부** 만족하면 F9 통과다. (2026-08-21 실측은 전 항목 통과)

1. **평균 프레임**: 서버·클라 모두 10s 창 평균 fps ≥ **54** (환경 상한 58의 ~93%) — S1·S2 지속 구간 전 창. 시나리오 기동 직후 첫 창 1개는 제외.
2. **스파이크**: **100ms 초과 프레임 0건** (기동 창 포함 전 구간).
3. **틱 레이트**: 세 맵 모두 **2.5틱/s ± 2%** (60초 이상 관측, 부하 중 포함).
4. **오류**: 런타임 Error/Warning **0건**.
5. **cue 규율**: 부하 중에도 cue 는 F5 §4 쿨다운의 `play`→`suppressed` 짝을 유지 (기존 A4 판정과 동일 — 로그로 확인).

**권고 (판정선 아님)**: 릴리스 전 `[Worker N] simTick` 행·`[WorkerFx]`·`[MineSound]` 의 매 액션 로그를 축소(또는 플래그화)할 것. 분당 1,300건은 실플레이 진단 시 실제 신호를 묻는다. 축소하더라도 §6 재측정 절차가 쓰는 `[Perf]`·`[VeinTick] layout`·오류 로그는 남긴다.

## 6. 재측정 절차 (회귀 점검용)

전제: 프로필 원복 규율은 `docs/17` §0.2-A 를 따른다 — 단, baseline 표가 아니라 **검증 직전 상태**로 되돌린다 (개발 프로필은 오너 실진행분).

1. `refresh` → 빌드 로그 오류 0 확인 → `clear_logs` → `play`.
2. **스냅숏** (server_main): `svc._T.f9Snapshot = _HttpService:JSONEncode(svc:GetProfile())` + 요약 로그 (`svc` = 플레이어 엔티티의 `script.AccountProfileService`).
3. **프로브 on** (server_main·client 각각): `_PerfProbeLogic:ResetWindow()` · `_PerfProbeLogic.Active = true`. 기준선 30초 수집.
4. **일꾼 5명**: `svc:PurchaseNextWorker(0, 0, 0, 0)` 를 5명 될 때까지 반복 (0비용 — 스냅숏이 되돌린다).
5. **S1**: 5명 전원 `w:RunProgram(기본왕복)` → 60초 수집. 틱은 시작·끝에 `sim.CurrentTick` + `ServerElapsedSeconds` 샘플, (Δtick/Δ초) 산출.
6. **S2**: 전원 `StopProgram` → `ResetInventory` → 30블록 조건 프로그램 `RunProgram` → 60초 수집 (같은 방식).
7. **원복**: 전원 `StopProgram` → `svc:RestoreProfileSnapshot(svc._T.f9Snapshot)` → `svc:RestoreCurrentWorkerState()` → `MarkProfileDirty` → `SaveProfileAndWait` → post 요약 로그가 pre 와 일치하는지 대조. 프로브 `Active = false` (양쪽).
8. `logs(kind="normal")` 에서 `[Perf]` 창들·틱 샘플·Error/Warning 수를 §5 판정선과 대조.

⚠️ 함정: ① 스냅숏(`_T`)은 Play 세션 안에서만 산다 — 스냅숏과 원복은 **같은 세션**에서 끝낼 것 ② 원복 후 `RestoreCurrentWorkerState()` 를 빼먹으면 저장 경로의 `CaptureCurrentWorkerState` 가 부하 중 런타임 값을 도로 담아 간다 ③ 판정은 post 로그와 pre 로그의 **필드 일치**로 한다.

## 7. 한계·후속

- **실기기 절대치 미확인**: Maker 시뮬레이션 수치다. 출시 빌드에서 오너가 실플레이 중 끊김(체감 스터터) 없음을 1회 확인하면 충분하다 — 별도 티켓을 만들 근거는 현재 없다.
- **맵 전환 순간의 스파이크 미측정**: 개발 프로필이 깊은/보석 광산 미해금이라 부하 중 전환은 치지 않았다. 기능 무결은 기존 A6(맵 3개 전환·BGM 무중단)에서 확인됨. 해금 프로필로 재측정할 기회가 있으면 §6 에 전환 1회를 끼워 넣는 것을 권장.
- **멀티 유저·모바일**: MVP 범위 밖 (T-09 보류). 동시 접속 잠금이 1인 세션을 보장한다 (F7-A).
- **메모리/GC 직접 측정 API 없음**: 단일 프레임 스파이크(≤97ms, 기동 순간)로 간접 관찰만 가능하다.
