# F8. 메이플 디거 — 서버 거절 사유 카탈로그

> 작성일: 2026-07-31
> 목적: 서버가 요청을 거절할 때 **어떤 사유가 존재하고, 어떤 문구로, 어디에 보여 줄지**를 한곳에서 정한다.
> 근거: `docs/16` §14 **D-10**(판매 거절 사유 미표시), 코드 전수 조사(2026-07-31)
> 관련: F7-A §4(실패·복구 UX), F7-B §5.5(서버 API), F5 §6(화면 영역 분할)

## 0. 왜 이 문서가 필요했나

**D-10은 "판매가 안 되는데 이유를 알 수 없다"였다.** 서버는 거절 사유를 정확히 만들어 보내고 있었는데 **화면에 그릴 자리가 없어서** 사용자에게는 "그냥 안 되는 것"으로 보였다.

이 결함은 화면 하나의 문제가 아니라 **구조의 문제**다. 지금은 거절 사유가 코드에 한국어 문자열 리터럴로 흩어져 있고, 표시 자리는 두 곳뿐이며, 어느 요청의 결과인지 식별할 방법이 없다. **T-02(맵 강화) · T-05(프로그램 라이브러리) · T-06(외형·가챠)이 각각 새 거절 경로를 만들면 D-10이 그대로 재발한다.**

## 1. 현재 메커니즘

### 1.1 전달 경로

```
서버 (AccountProfileService / EconomyService / ProgressionService)
  └─ profile:SetTransactionMessage("...")   ← 한국어 문장을 직접 대입
       └─ @Sync property string LastTransactionMessage
            └─ 클라이언트가 폴링해서 텍스트에 그린다
```

`LastTransactionMessage`는 `AccountProfileService`의 **`@Sync` 문자열 하나**다(`AccountProfileService.mlua:93`).

### 1.2 표시 자리 — 현재 2곳뿐

| 화면 | 슬롯 | 구현 |
|---|---|---|
| `MineSelectUI` SelectPanel | `feedbackText` | `MineSelectController.mlua:154` |
| `MineSelectUI` 판매 패널 | `saleFeedbackText` | `MineSelectController.mlua:269` `RefreshSaleFeedback` |

판매 패널 슬롯은 **D-10을 고치면서 급히 추가한 것**이다. 코드 주석이 그 경위를 남기고 있다 — *"판매 패널을 열면 SelectPanel이 꺼지므로 거부 사유가 화면에서 사라졌다"*(`MineSelectController.mlua:270-272`).

`BlockProgramUI`는 **별도의 클라이언트 전용 피드백**(`BlockProgramController.feedbackText`)을 쓴다. 서버 거절이 아니라 블록 조립 검증 결과다. `AccountRecoveryUI`는 `messageText`에 `SessionMessage` / `RecoveryStatus`를 그린다 — 이것도 별개 채널이다.

## 2. 발견한 문제 4건

### 2.1 같은 조건에 서로 다른 문구가 존재한다 ★

`ProgressionService`(선검증)와 `AccountProfileService`(최종 검증)가 **같은 상황에 각각 메시지를 쓴다.** 어느 쪽이 먼저 걸리느냐에 따라 사용자가 보는 문장이 달라진다.

| 조건 | `ProgressionService` | `AccountProfileService` |
|---|---|---|
| 미보유 일꾼의 수레 강화 | "보유한 일꾼만 수레를 강화할 수 있습니다." (`:104`) | "보유하지 않은 일꾼은 수레를 강화할 수 없습니다." (`:858`) |
| 수레 최대 용량 | "수레 적재량이 최대입니다. (50칸)" (`:112`) | "일꾼 N의 수레는 최대 용량입니다." (`:862`) |
| 일꾼 5명 초과 | "이미 최대 5명의 일꾼을 보유하고 있습니다." (`:94`) | **같은 문장** (`:821`) — 문자열이 두 곳에 복제돼 있다 |

**세 번째 항목이 특히 위험하다.** 같은 문장이 두 파일에 복제돼 있어, 한쪽만 고치면 조용히 갈라진다.

### 2.2 메시지에 소유권이 없다

`LastTransactionMessage`는 **전역 슬롯 하나**이고 성공·실패가 같은 필드를 공유한다. 다음이 구분되지 않는다.

- 사용자가 방금 누른 버튼의 결과인가, **백그라운드 자동 판매**의 결과인가
- 판매 패널의 결과인가, 광산 선택 패널의 결과인가
- **언제 지워야 하는가** — 현재 코드는 `~= ""` 로만 판단하므로 한 번 쓰인 메시지가 계속 남는다

자동 판매는 하역할 때마다 서버가 실행하므로(F7-B §2), **사용자가 일꾼 구매에 실패한 직후 자동 판매가 성공 메시지를 덮어쓰면** 실패 사유가 사라진다.

### 2.3 신규 화면에는 표시 자리가 없다

T-03 맵 강화 패널 · T-05 프로그램 라이브러리 · T-06 외형/도감/가챠는 **전부 새 거절 경로를 만든다.** 지금 구조로는 각 담당자가 슬롯을 따로 만들고 문구를 새로 지어야 하며, 그 과정에서 §2.1 같은 불일치가 늘어난다.

### 2.4 자동화 중 실패는 화면에 전혀 나타나지 않는다

일꾼이 틱마다 겪는 실패는 **로그에만 남는다.**

| 실패 | 의미 | 현재 처리 |
|---|---|---|
| `vein_empty` | 광맥 stage 0 — 캘 것이 없다 | 로그만 |
| `hand_full` | 손에 이미 광물이 있다 | 로그만 |
| `cart_full` | 수레가 가득 | 로그만 |
| 맵 전환 거절 | `missing-player` / `unknown-target` / `missing-source` / `profile-save` (`MineTransitionService.mlua:15~35`) | `log_error`만 |

**D9 §5.2가 발견한 "일꾼 2를 사도 채굴량이 0"인 상황이 화면에 드러나지 않는 이유가 이것이다.** 일꾼은 매 틱 `vein_empty`로 실패하는데 사용자는 아무것도 보지 못한다.

## 4. 문구 작성 규칙

D-10의 교훈은 "자리를 만들어라"였지만, 자리만 있고 문장이 나쁘면 같은 문제가 반쯤 남는다.

1. **무엇이 부족한지 숫자로 말한다.** "재화가 부족합니다"가 아니라 "골드가 40 부족합니다 (필요 180 / 보유 140)". §3.3·§3.4·§3.5의 `INSUFFICIENT` / `REQUIREMENTS` 계열이 전부 이 규칙을 어기고 있다.
2. **다음 행동을 알려준다.** "10단계 뒤에만 판매할 수 있습니다"는 좋다 — 무엇을 하면 풀리는지 말한다. "알 수 없는 광산입니다"는 나쁘다 — 사용자가 할 수 있는 게 없다(이건 **버그 신호**이므로 사용자 문구가 아니라 로그여야 한다).
3. **같은 조건에는 같은 문장을 쓴다.** §2.1의 불일치를 없앤다. 문구는 **한 곳에서만 정의**하고 다른 계층은 코드만 넘긴다.
4. **저장 실패는 롤백 사실을 함께 알린다.** "판매 저장에 실패했습니다"만으로는 골드가 나갔는지 알 수 없다. "판매 저장에 실패해 되돌렸습니다. 다시 시도해 주세요."
5. **버그성 거절은 사용자 문구를 만들지 않는다.** `MINE_UNKNOWN`, `MAP_TRANSITION_missing-player` 등은 정상 플레이에서 나올 수 없다. 로그로 남기고 화면에는 일반 문구("요청을 처리하지 못했습니다")를 쓴다.

## 5. 신규 화면이 지켜야 할 계약

**T-03 · T-05 · T-06 담당자는 이 절만 지키면 D-10을 재발시키지 않는다.**

1. **거절 사유를 그릴 자리를 화면에 먼저 만든다.** 버튼을 만들기 전에 만든다. 자리가 없으면 사유가 사라진다.
2. **모달을 열 때 이전 메시지를 지운다.** `LastTransactionMessage`는 전역 슬롯이라 다른 화면의 결과가 남아 있을 수 있다(§2.2).
3. **`RefreshUI`의 변경 감지 키에 메시지 필드를 넣는다.** 빠지면 사유가 바뀌어도 화면이 갱신되지 않는다 — T-01에서 실제로 겪은 무증상 실패다(`docs/16` §16).
4. **클라이언트에서 거절 여부를 재계산하지 않는다.** 서버가 준 문구를 그대로 그린다. 버림·만분율·하한 때문에 클라이언트 계산은 서버와 어긋난다(F7-B §5.6.3).
5. **성공 메시지와 실패 메시지를 같은 자리에 그려도 된다.** 다만 **색으로만 구분하지 않는다**(D5 §8 V1). 접두어나 아이콘을 함께 쓴다.

## 6. T-02 · T-05 · T-06이 추가할 거절 경로

각 티켓이 새로 만들 사유를 미리 잡아 둔다. **구현 시 이 표에 실제 문구를 채운다.**
