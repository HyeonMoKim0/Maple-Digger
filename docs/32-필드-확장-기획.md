# D10. 광산 필드 확장 기획 (배경 = 필드, 광산 레벨 1~5)

> 작성: 2026-08-26 (post-MVP 신규 기획). MVP는 `docs/00` 기준 완료 판정을 받았고(T-17까지, 오너 검수만 잔여), 이 문서는 **그 이후에 착수하는 별도 확장 기능**을 다룬다. `docs/07`(D6)·`docs/09`(F6)·`docs/13`(F7-B) §5의 기존 계약은 이 문서가 명시적으로 언급하지 않는 한 그대로 유지된다.
> 결정 근거: 오너와의 2026-08-26 대화에서 4개 질문에 답변을 받았다(§2 참조). 이 문서가 그 결정을 반영한 단일 기준이다.
>
> **구현 상태 (2026-08-26)**: **P0(서버 스키마·로직) + P1(초보 광산 레벨 2 샘플 1개) 구현·Play 실측 검증 완료.** `VeinTickSimulator`(§7 `FieldLevelDefinitionsJson`·`FieldLevel`·`ApplyFieldLevel`·`LoadFieldLevelDefinitions`·격자/경계 돌멩이 스폰)·`AccountProfileService`(§6 `fieldLevels`·비용 계산·`PurchaseFieldUpgrade`·`PushFieldLevelToSimulator`)·`ProgressionService`(§6.1 `RequestFieldUpgrade`·`GetFieldUpgradeCost`)에 반영됐고, `beginner_mine`(farm01)에 레벨 2 실제 데이터(§3.2)를 저작해 **필드 확장 구매 → 타일 개방 → 일꾼이 실제로 걸어가 새 광맥을 채굴 → 경계 밖은 여전히 차단**까지 `maker_execute_script`로 전 구간 실측했다(§8.4). 경계 돌멩이·격자 점선 오버레이 **둘 다 스크린샷으로 정상 렌더링 확인 완료**(§8.5 — 격자는 계정 스토리지 API 업로드 대신 Maker "Import Image"로 재업로드해 해결). 기존 세 맵의 레벨 1 동작은 무회귀(Play 실측 확인).

## 0. 배경과 목적

기존 화면(스크린샷 기준)은 초록색 사각 필드(이동·채굴 가능 공간)와 그 바깥의 동굴 배경 이미지(`docs/21` §11, 2026-08-26 추가)가 분리되어 있었다 — 배경은 순수 장식이고 타일 필드 크기는 세 광산 모두 고정값(10×10 / 14×8 / 20×12)이었다.

이 기획은 이를 다음으로 바꾼다:
- **필드 자체를 광산 배경 이미지 위 공간으로 통합한다.** 더 이상 "초록 잔디 필드 + 바깥 장식 배경"이 아니라, 배경 이미지 안의 일부 구역이 곧 이동·채굴 가능 필드다.
- **광산마다 1~5레벨의 "필드 레벨"을 도입한다.** 레벨이 오르면 이동 가능 필드와 광맥이 나오는 공간이 함께 넓어진다.
- **필드 가장자리에는 돌멩이로 경계를 표시**하고, **필드 안에는 흐릿한 점선 격자**로 칸을 구분한다.

## 1. 용어 정리 (중요 — 기존 "맵 강화"와 혼동 금지)

`docs/07` §4의 "광산 강화 효과"라는 표현과 `docs/13` §5의 "맵 강화"는 **이미 구현되어 있는 기존 시스템**(레벨 0~10, 획득량·회복·희귀확률·특별광맥 4종 스탯 보너스)을 가리킨다. 이번에 새로 도입하는 것은 **완전히 별도의 시스템**이므로(§2 결정 1), 이 문서에서는 다음 용어로 고정해 구분한다.

| 용어(이 문서) | 가리키는 것 | 레벨 범위 | 효과 | 문서 |
|---|---|:--:|---|---|
| **맵 강화** (기존, 불변) | 스탯 4종 보너스 | 0~10 | 획득량·회복 속도·희귀확률·특별광맥 가속 | `docs/13` §5 |
| **필드 확장** (신규, 이 문서) | 이동·채굴 가능 공간 크기 | 1~5 | 필드 크기 + 광맥 배치 공간 확장 | 이 문서 |

> UI 버튼 라벨(예: "필드 확장" vs "광산 개척" 등 플레이어向 문구)은 확정 사항이 아니다. `msw-ui-system`으로 화면을 만들 때 오너 확인을 받는다. 코드 심볼은 `FieldLevel`(맵별 1~5)로 제안하며, 기존 `MineLevel`/`mineLevels`(맵 강화 0~10, `docs/13` §5.1)와 이름이 겹치지 않게 한다.

## 3. 필드 확장 규칙

### 3.1 레벨 1 = 현재 구현 그대로

**레벨 1의 필드·광맥 배치는 지금 이미 구현·검증된 값을 그대로 쓴다** — 변경하지 않는다. 즉:

| MineId | 레벨 1 필드 크기 | 레벨 1 광맥 배치 |
|---|---:|---|
| `beginner_mine` (`farm01`) | 10×10 | `docs/07` §3 표의 현재 배치 그대로 |
| `deep_mine` | 14×8 | 동일 |
| `gem_mine` | 20×12 | 동일 |

이렇게 두는 이유: 이미 Play 검증·오너 검수(`docs/16`, `docs/29`)를 통과한 배치를 그대로 "레벨 1 기준선"으로 삼으면, 이번 확장이 **기존 검증 결과를 무효화하지 않는 순수 추가(additive) 작업**이 된다. 레벨 2~5만 새로 설계하면 된다.

### 3.2 레벨 2~5 = 동심 방향 확장 (확정 좌표 제안, 2026-08-26 실측 반영)

- Depot는 항상 `(0,0)`에 고정한다(기존 원칙 유지, `docs/07` §1).
- **실측 확인**: 세 맵 모두 **1칸(cell) = 1월드유닛**이다(`MapBuilder`로 marker `TransformComponent.Position`과 `VeinTickSimulator`의 `cellX/cellY`를 대조해 확인 — 예: `farm01`의 `VeinMarker01`은 `cellX=1,cellY=0`이고 실제 `Position=(1,0,0)`). 따라서 셀 범위를 그대로 월드 좌표 범위로 써도 된다.
- **성장 방식: 레벨 1 사각형을 사방으로 균등 패딩(padding)한다.** 레벨 1의 기존(이미 검증된) 바닥 범위를 그대로 두고, 레벨이 오를 때마다 그 바깥으로 한 겹씩 정사각형 링을 두른다. 패딩이 좌우·상하 대칭이므로 **필드의 중심점은 레벨 1~5 내내 변하지 않는다** — 이는 §8의 배경 재계산을 크게 단순화한다(중심 좌표는 그대로 두고 배율만 올리면 된다).
- **패딩 표(초안 — Play 테스트·오너 미감 확인 대상)**: 레벨 1 대비 각 변에 더해지는 칸 수(누적).

  | 레벨 | 각 변 패딩(누적) |
  |:--:|:--:|
  | 1 | +0 (기존 그대로) |
  | 2 | +1 |
  | 3 | +2 |
  | 4 | +3 |
  | 5 | +4 |

- **맵별 레벨 범위(셀, 실측한 레벨 1 값 기준 계산)**:

  | 맵 | 레벨 | 셀 범위 (x / y) | 크기 | 레벨1 대비 면적 |
  |---|:--:|---|---:|---:|
  | `beginner_mine`(`farm01`) | 1 (기존) | x −4..5 / y −6..3 | 10×10 | 1.00× |
  | | **2 (✅ 저작·실측 완료 2026-08-26, §8.4)** | x −5..6 / y −7..4 | 12×12 | 1.44× |
  | | 3 | x −6..7 / y −8..5 | 14×14 | 1.96× |
  | | 4 | x −7..8 / y −9..6 | 16×16 | 2.56× |
  | | 5 | x −8..9 / y −10..7 | 18×18 | 3.24× |
  | `deep_mine` | 1 (기존) | x −3..10 / y −5..2 | 14×8 | 1.00× |
  | | 2 | x −4..11 / y −6..3 | 16×10 | 1.43× |
  | | 3 | x −5..12 / y −7..4 | 18×12 | 1.93× |
  | | 4 | x −6..13 / y −8..5 | 20×14 | 2.50× |
  | | 5 | x −7..14 / y −9..6 | 22×16 | 3.14× |
  | `gem_mine` | 1 (기존) | x −3..16 / y −7..4 | 20×12 | 1.00× |
  | | 2 | x −4..17 / y −8..5 | 22×14 | 1.28× |
  | | 3 | x −5..18 / y −9..6 | 24×16 | 1.60× |
  | | 4 | x −6..19 / y −10..7 | 26×18 | 1.95× |
  | | 5 | x −7..20 / y −11..8 | 28×20 | 2.33× |

  이 값은 **초안**이다 — 실제 배치 시 맵 작성자가 RectTileMap 바닥 타일을 이 범위까지 미리 깔아 두고(§3.3), Play 테스트·오너 미감 판정(§10 E-항목)으로 패딩 수치를 조정할 수 있다. 특히 레벨 5의 면적 배율이 맵마다 다른데(3.24×/3.14×/2.33×), §8의 배경 배율 계산 결과 `gem_mine`은 아트 해상도 부담이 가장 크므로(§8) 패딩을 줄이는 조정 1순위 후보다.

### 3.3 링별 광맥 배치 — 규칙(수작업 배치의 기준)

Q3 결정에 따라 **레벨마다 셀 좌표를 기획자가 직접 손으로 배치**한다(정확한 좌표는 이 문서가 아니라 실제 `.map` 작업 시 Maker에서 시각적으로 확인하며 확정한다). 그 수작업이 따를 배치 규칙:

1. **광물 종류는 그대로 유지한다** — 새 링에도 그 광산이 이미 쓰는 종류(`stone`/`iron`/`stone·iron`/`stone·iron·gold`)만 배치한다. 새 광물 종류 추가는 필드 확장의 역할이 아니다(§3.2).
2. **레벨당 광맥 2~3개를 새 링 안에 추가한다.** 기존 레벨 1 밀도(예: `farm01` 6개/100칸 ≈ 0.06개/칸)보다 약간 낮은 밀도를 목표로 한다 — 새로 열린 공간이 "휑하지 않되 빽빽하지도 않게".
3. **거리에 비례해 `recoverTicks`(회복 소요)를 늘린다** — 기존 레벨 1의 근거리(`recoverTicks 5`) → 원거리(`recoverTicks 15`) 패턴을 그대로 새 링에도 적용한다. 링이 바깥일수록(레벨이 높을수록) 회복이 더 오래 걸리는 광맥을 배치해 "더 넓은 필드 = 왕복 동선이 길다"는 자동화 설계 재미를 유지한다.
4. **일꾼 시작점(`WorkerStarts`)은 이동하지 않는다.** 5명 시작 셀은 레벨 1 배치를 그대로 쓴다 — 필드가 넓어져도 시작 위치가 바뀌면 기존 저장된 위치 감각이 깨진다.
5. **특별 광맥 후보(`SpecialVeinCandidates`)는 레벨 5(최대)에서만 추가한다.** 레벨 2~4 진행 중에는 기존 4~6개 후보를 그대로 쓰고, 레벨 5에 도달했을 때 새 링에 1~2개 후보를 추가하는 정도로 제한한다 — 특별 광맥 후보를 레벨마다 늘리면 §7 검증·§6 API 계약이 불필요하게 복잡해진다.
6. 배치 후 `docs/07` §7 "맵 작성 절차"와 동일한 순서(레이아웃 확정 → marker 연결 → 검증)를 레벨별로 반복한다.

### 3.3 이동 가능 판정

`VeinTickSimulator`/`WorkerController`가 참조하는 "이동 가능 셀" 판정에 **레벨 종속 조건**을 추가한다: 셀이 RectTileMap 상 바닥이어도, 현재 `FieldLevel`이 그 셀이 속한 링을 아직 열지 않았다면 이동 불가로 취급한다. 미해금 구역의 광맥·Depot 상호작용 API(`TryMine`, `AddToDepot` 등)도 동일하게 거절한다.

## 4. 경계 표시 (돌멩이)

- **성격: 순수 시각 장식, 채굴 불가.** 기존 채굴 대상 광물 "돌(`stone`)"과 헷갈리지 않도록, 경계 돌멩이는 상호작용 컴포넌트 없이(트리거·채굴 API 대상 아님) 배치만 되는 시각 전용 엔티티로 정의한다. 이름 충돌을 피하기 위해 코드/모델 이름은 `BoundaryRock`(가칭)으로 하고 광물 `stone`과 완전히 분리한다.
- **배치 규칙**: 현재 열린 필드의 바깥 테두리 셀(그다음 링과 맞닿는 경계)을 따라 한 줄로 배치한다. 레벨업 시 이전 테두리의 돌멩이는 사라지고(또는 갱신되고) 새로 열린 필드의 바깥 테두리에 다시 배치된다.
- **스프라이트 후보 (2026-08-26, `msw-search` 탐색 결과 — 오너 확인 전 후보일 뿐, 최종 승인은 `docs/21` 방식대로 월드 배치 후 육안 판정)**:

  | 후보 | RUID | 크기 | 특징 |
  |---|---|---:|---|
  | **1순위 추천 — 오너 승인 (2026-08-26)** | `65a4cbae9ac840c3bb214e8079d39006` | 84×100 | 회색 각진 암석 무더기. 채색이 중립적이라 세 광산 어디에도 무난하게 어울림 |
  | 2순위 | `c62eb4cbda7e41608d79548e53b93854` | 84×60 | 청회색 둥근 돌무더기. 낮고 넓어 시야를 덜 가림 |
  | 3순위(테마 강조) | `9dc823eb6b4e414bb79b77bc478be953` | 112×40 | 어두운 석탄 더미. "광산"다운 색감이지만 어두워 그림자와 겹치면 묻힐 수 있음 |

  **채굴 대상 `stone` 광물(RUID `0f44530d655f4e33bfbe43423450ee9f`)과 대조 확인 완료** — 그쪽은 청록색 발광 크리스탈이라 위 회색·갈색 계열 돌 후보와 형태·색 모두 명확히 구분된다(§4 "채굴 불가" 원칙과 부합).

  최종 선택은 `msw-asset-verify` 스킬 절차대로 월드에 실제로 배치해 화면으로 판정한 뒤 `docs/21`에 승인 절을 추가한다.
- **구현 형태**: `DepotMarker`/`VeinMarker`와 같은 맵 스코프 마커 패턴을 따르되, 서버 상태를 갖지 않는 순수 클라이언트 시각 요소로 두는 편이 가볍다(§9 미결 — 구현 시 확정).

## 5. 격자 안내선 (점선)

- **표시 범위: 현재 레벨에서 열린(이동 가능한) 필드 내부만.** 아직 열리지 않은 바깥 구역에는 격자를 표시하지 않는다 — 배경 동굴 이미지 그대로 두어 "아직 개척 안 된 구역"이라는 인상을 유지한다.
- **스타일**: 흐릿한(반투명, 알파 낮음) 점선 사각형으로 각 셀 경계를 표시한다. 진하게 튀지 않아야 하며, 기존 광맥·일꾼·마커 시인성을 해치지 않는다.
- **구현 방식**: 셀 하나 크기의 "점선 테두리" 스프라이트를 필드 전체 셀에 타일링 배치하는 방식을 제안한다(런타임 벡터 드로잉이 아님 — MSW 2D 렌더러 특성상 스프라이트 타일링이 안전하다). `docs/21` §11의 배경 렌더 순서 주의사항(SortingLayer가 OrderInLayer보다 우선한다, `platform.md` §6)이 이 격자 스프라이트에도 그대로 적용된다 — 바닥 타일 위·마커/캐릭터 아래로 오도록 SortingLayer를 맞춰야 한다.
- **스프라이트 확보 (2026-08-26)**: "칸 하나를 흐릿한 점선으로 두르는 정사각 테두리"에 정확히 맞는 기성 리소스는 없었다(모서리만 표시하는 대시형 "선택 프레임" 계열만 발견 — 인접 칸끼리 경계선을 공유하지 못해 부적합 판단). **`msw-painter`로 직접 제작해 업로드 완료.**

  | 항목 | 값 |

  | RUID | **`392c583147a64a698f854aa446ede090`** |
  | 이름 / 분류 | `mine-field-grid-cell` · sprite / etc |
  | 스타일 | chunky pixel — 32×32 논리 그리드, 점 단위(rect) 렌더로 안티에일리어싱 없음 |
  | 출력 크기 | 128×128, 투명 배경 |

## 6. 강화(레벨업) 조건·비용

기존 맵 강화(`docs/13` §5.4)와 같은 스타일을 쓰되 완전히 별도 표로 정의한다.

| 항목 | 규칙 |
|---|---|
| 범위 | 맵별 `FieldLevel` **1~5** (해금 직후 기본값 1) |
| 강화 횟수 | 레벨 1→5, 총 4회 |
| 소유 | 계정 공용, 맵마다 독립 레벨 (기존 `mineLevels`와 별개 필드 — 예: `AccountProfile.progress.fieldLevels`) |
| 조건 | 해당 광산에 입장한 상태에서만 요청 가능 (기존 맵 강화와 동일 제약, `docs/13` §5.4) |
| 적용 시점 | **즉시 적용, 일꾼 프로그램 중단 없음.** 맵 전환과 달리 필드 확장은 같은 맵 안의 변화이므로 실행 중인 프로그램을 정지시키지 않는다. 새로 열린 구역의 이동·채굴은 그 즉시 허용된다. |

비용표(초안, Play 테스트로 조정 — `docs/13` §3의 관례를 따른다):

```text
레벨 n → n+1 (n = 1~4, n = 현재 레벨)
골드      floor(80 × 1.8^(n-1))   -- 반올림 아님, 버림
대표 광물  40 × n
```

레벨 1→2가 골드 80 + 대표 광물 40, 레벨 4→5가 골드 466 + 대표 광물 160이다(2026-08-26 P0 구현·`maker_execute_script` 실측으로 검증 — 레벨1→2 실측 80/40, 레벨2→3 다음 비용 144/80 확인). 기존 맵 강화(레벨 0→10 누적 골드 약 1,638)보다 단계 수는 적지만 레벨당 비용을 높게 잡아, "필드 확장"이 "맵 강화"보다 더 묵직한 결정으로 느껴지게 한다 — 실제 곡선은 Play 테스트로 조정한다.

## 8. 배경 아트에 미치는 영향 (중요 — 기존 결정과 충돌)

`docs/21` §11(2026-08-26 작성)의 배경 배율·중심 좌표는 **현재(레벨 1) 필드 크기에 맞춰 "타일 바깥에는 얇은 여백만" 남도록 딱 맞게 계산됐다** — 배율 공식 `scale = max((W+3.2)/16.72, (H+3.2)/9.41)`가 레벨 1 필드 크기 `W×H`(월드유닛)를 기준으로 배경을 씌운 것이다.

이번 기획대로 레벨 5까지 필드가 넓어지려면, **배경 이미지가 덮는 실제 공간이 레벨 1 필드보다 훨씬 커야 한다** — 배경의 배율은 **레벨 5(최대) 필드 크기를 기준으로 다시 계산**해야 한다.

### 8.1 레벨별 배율 재계산 (§3.2 패딩 표 기반, 같은 공식 적용)

**핵심 단순화**: §3.2의 패딩이 좌우·상하 대칭이므로 **필드 중심점은 레벨 1~5 내내 동일**하다. 즉 `docs/21` §11에 이미 있는 맵별 중심 좌표(`farm01`=(1,−1), `deep_mine`=(4,−1), `gem_mine`=(7,−1))는 **레벨과 무관하게 그대로 쓴다** — 레벨업 때 `MineBackground`의 `TransformComponent.Position`은 손댈 필요가 없고, **`Scale`만 다음 표대로 올리면 된다.**

| 맵 | 레벨 | 필드 W×H | 배율(scale) |
|---|:--:|---:|---:|
| `farm01` | 1 | 10×10 | **1.40**(기존) |
| | 2 | 12×12 | 1.62 |
| | 3 | 14×14 | 1.83 |
| | 4 | 16×16 | 2.04 |
| | 5 | 18×18 | **2.25** |
| `deep_mine` | 1 | 14×8 | **1.19**(기존) |
| | 2 | 16×10 | 1.40 |
| | 3 | 18×12 | 1.62 |
| | 4 | 20×14 | 1.83 |
| | 5 | 22×16 | **2.04** |
| `gem_mine` | 1 | 20×12 | **1.62**(기존) |
| | 2 | 22×14 | 1.83 |
| | 3 | 24×16 | 2.04 |
| | 4 | 26×18 | 2.25 |
| | 5 | 28×20 | **2.47** |

- 그 결과 레벨 1 상태에서는 배경이 지금과 동일하게(레벨1 배율 그대로) 보이고, 레벨업할 때마다 **배경이 서서히 커지며 필드를 따라잡는 것이 아니라 필드가 배경 안에서 확장돼 가는** 그림이 된다 — 정확히는 반대다: **배경 자체가 레벨업 시점마다 그 레벨의 배율로 다시 스케일된다.** 레벨 1 상태에서는 지금 손님이 보는 좁은 배율의 배경만 있고, 그 바깥은 아직 렌더링되지 않는다는 뜻이 아니라 — **처음부터 레벨 5 배율(최대 크기)의 배경을 깔아 두고, 낮은 레벨에서는 그 초과분이 이동 불가 구역(§4 돌멩이 경계)에 가려 보이지 않게 하는 쪽**이 §2 결정 2("최대 크기로 미리 제작 + 단계적 개방")와 일관된다. 즉 **`MineBackground`도 레벨 1부터 레벨 5 배율(위 표의 마지막 행)로 배치하고, 배율 자체는 레벨업 때 바꾸지 않는다.** 위 레벨별 배율 표는 "이 레벨에서 최소 이만큼은 덮어야 한다"는 하한 검증용으로 쓰고, 실제 `Scale` 값은 처음부터 레벨 5 행의 값(예: `farm01` 2.25)을 쓰는 쪽을 권장한다 — 레벨업마다 배경 크기가 바뀌면 크리스탈·레일 장식의 화면상 위치가 매 레벨 흔들려 어색하다.

### 8.2 아트 해상도 경고 — `gem_mine` 우선 확인 필요

`docs/21` §11은 이미 "배율을 2.3배로 늘리면 1672px 원본이 흐려진다"고 기록해 뒀다(당시는 카메라 최대 줌아웃 대응 검토였다). 레벨 5 배율이 이 근방이거나 넘는 맵이 있다:

| 맵 | 레벨 5 배율 | 비고 |
|---|---:|---|
| `farm01` | 2.25 | 근접 — 경계선 |
| `deep_mine` | 2.04 | 여유 있음 |
| `gem_mine` | **2.47** | **초과 — 흐려짐 위험 가장 높음** |

> **결정 (2026-08-26, 오너)**: **원본 배경 이미지를 고해상도로 재요청**하는 쪽으로 확정했다(3000px 폭 이상 권장 — 현재 원본은 1672×941). **오너 액션 아이템**: 동일한 구도(크리스탈·레일·랜턴 배치)의 고해상도 버전을 준비해 전달하면, 받는 즉시 `docs/21` §11에 새 RUID로 교체 등재하고 이 문서의 배율표(§8.1)를 재검증한다. 고해상도 원본이 아직 없는 동안에는 §3.2/§8.1의 좌표·배율 값은 그대로 유효하며(레벨 범위 자체는 해상도와 무관), 구현은 기존 저해상도 원본으로 우선 진행하고 자산 교체는 나중에 반영해도 된다.

### 8.3 기존 "알려진 한계 — 최대 줌아웃" 항목과의 관계

`docs/21` §11의 카메라 최대 줌아웃(38.4×21.6 unit) 노출 문제는, 레벨 5 배경이 지금보다 커지면서 함께 완화된다 — 배경이 커질수록 줌아웃 시 가장자리가 보일 여지가 줄어든다. 다만 8.1의 "레벨 1부터 레벨5 배율을 쓴다" 방식을 채택하면, 레벨 1 상태에서는 오히려 **필드보다 배경이 상대적으로 훨씬 커 보이는** 새로운 미감 이슈가 생길 수 있다 — 이 부분은 실제로 화면을 보며(Play 테스트) 오너가 판정해야 한다(§10 E6).

### 8.4 P1 실측 결과 (2026-08-26, `beginner_mine` 레벨 2 샘플)

§3.2의 패딩 표대로 `farm01`(`beginner_mine`)에 실제 레벨 2 데이터를 저작하고 Play에서 전 구간을 확인했다.

**저작한 데이터**:
- `VeinTickSimulator.FieldLevelDefinitionsJson`에 레벨 2 정의 1건 추가 — 범위 x −5..6 / y −7..4(§3.2 표와 동일), 신규 광맥 2개(`vein-stone-07` at (−5,−2), `vein-stone-08` at (6,3), 둘 다 `recoverTicks=20` — §3.3 규칙 3 "원거리일수록 회복 느리게"에 맞춰 레벨1 최원거리 값(15)보다 더 크게).
- 신규 광맥마다 기존 `MineMarker.model`(`RootDesk/MyDesk/Models/Mine/MineMarker.model`)을 `modelId`로 배치한 `VeinMarker07`/`08` 2개 — 기존 6개 마커와 동일한 저작 방식(§0 "레벨마다 수작업으로 직접 배치" 결정과 일치).

**구현 중 발견해 수정한 버그**: `VeinTickSimulator.ApplyFieldLevel`이 `RectTileMapComponent:BoxFill`을 정수 `tileIndex`(0)로 호출했는데, 실측 결과 `.map` JSON의 `tileIndex` 값과 런타임 `BoxFill`의 정수 오버로드가 대응하지 않아 `GetTile`이 `nil`을 반환했다(문자열 타일 이름 오버로드만 정상 동작). **수정**: 맵 진입 시 Depot 셀의 실제 `GetTile(...).Name`(farm01 실측값 `"Henesys_soil_1"`)을 읽어 `self._T.floorTileName`에 캐시하고, `BoxFill(self._T.floorTileName, ...)`로 호출하도록 바꿨다. 이 수정 전에는 계정 레벨은 올라가도 타일이 실제로는 열리지 않는 조용한 실패였다 — P1을 먼저 검증한 덕분에 15개 구간 전부에 이 버그가 퍼지기 전에 잡았다.

**실측 로그 증거** (`maker_execute_script`, 서버 컨텍스트):
```
[P1TEST2] before: FieldLevel=2 IsWalkable(-5,-2)=true        -- 로그인 시 계정 레벨이 자동 재적용됨
[AccountProfile] field upgraded mineId=beginner_mine level=3 gold=-144 ore=stone-80   -- §6 비용식과 일치
[VeinTick] field level up skipped mineId=beginner_mine level=3 reason=no-definition   -- 레벨3 미저작 → 안전하게 정지
[P1TEST2] after: IsWalkable(-5,-2)=true IsVein=true HasOre=true
[P1TEST2] after: IsWalkable(6,3)=true IsVein=true
[P1TEST2] still blocked outside ring: IsWalkable(-6,-2)=false
[Worker 1] RunProgram accepted blocks=8 - state=Running
[Worker 1] program finished    -- 일꾼이 (0,0)→(-5,-2)까지 실제로 걸어가 채굴 성공
```
스크린샷에서도 일꾼이 새로 열린 구역의 광맥을 채굴해 손에 "돌"을 든 상태와, 확장된 경계에 새 돌멩이 무더기가 놓인 것을 확인했다. 테스트로 건드린 계정 상태(골드·돌·필드 레벨)는 전부 원복했다.

### 8.5 해결된 블로커 — 격자 점선 오버레이가 렌더되지 않던 문제 (근본 원인 확정, 2026-08-26)

`FieldGridCell`(격자 점선)을 스폰하면 실제 그림 대신 엔진의 "리소스 로딩/사용 불가" 대체 아이콘(회색↔흰색 점 고리)이 계속 표시되는 문제가 있었다.

**근본 원인 확정**: `msw-mcp`의 `asset_create_account_resource_storage_item`(계정 리소스 업로드 API)로 만든 RUID는 백엔드 메타데이터·CDN 썸네일까지는 정상 생성되지만, **Maker 에디터 클라이언트가 참조하는 "내 리소스" 저장소에는 반영되지 않는다.** 오너가 Maker의 **Resource Storage → 내 리소스** 탭에서 이름·RUID 둘 다로 검색해도 결과가 0건으로 나와 확인했다 — API 업로드 경로와 Maker 클라이언트가 보는 리소스 목록이 서로 다른 저장소를 가리키는 것으로 보인다. (참고로 `56b7a052...` 같은 **기존에 정상 동작하던** 계정 리소스로 바꿔도 내 신규 `.model`에서는 똑같이 실패했던 것도 이 때문이다 — 그 리소스들은 애초에 Maker의 네이티브 업로드 경로로 들어왔기 때문에 정상 동작했던 것이다.)

**해결**: 같은 이미지를 **Maker 에디터 자체의 "Import Image" 기능**(Workspace 패널 → `MyDesk` 우클릭 → Import From → Import Image)으로 다시 업로드했다. 이 경로로 만든 리소스는 `RootDesk/MyDesk/*.sprite` 파일로 워크스페이스에 실제로 나타나며(예: `maple-digger-mine-field-grid-cell.sprite`), 새 RUID(`4c00158c8d6c454f8e6c5d7c5c09dd23`)를 `FieldGridCell` 모델에 연결하니 **정상 렌더링을 스크린샷으로 확인했다.**

**교훈 — 향후 커스텀 스프라이트가 필요할 때(경계 돌멩이 후보 재검토, P3 추가 자산 등)**: `msw-painter`로 그림을 만드는 것까지는 그대로 하되, **업로드 단계는 `asset_create_account_resource_storage_item` API 대신 Maker 에디터의 "Import Image"를 거쳐야 실제로 게임에서 렌더링된다.** 이번에 쓴 RUID(구, 미사용) `392c583147a64a698f854aa446ede090`는 참조가 끊긴 채로 계정 스토리지에 남아 있다 — 정리가 필요하면 오너가 직접 삭제해도 된다(코드에서 더 이상 참조하지 않음).
