## 1. 책임 분리

F5 §1의 "서버는 판정, 클라이언트는 표현" 경계를 그대로 승계한다. **볼륨은 어떤 게임 결과도 바꾸지 않으므로 전부 클라이언트 몫이다.**

| 구성 요소 | 실행 위치 | 책임 | 금지 |
|---|---|---|---|
| `SoundSettingsController` | **ClientOnly `@Logic`** | 볼륨 2종의 보관·변경·적용, BGM 재생/정지, (U1 채택 시) 프로필 저장 요청 | 게임 이벤트 판정, cue 선택 |
| `MineSoundController` | ClientOnly `@Component` (맵 3개) | F5 §4 쿨다운 판정 후 cue 재생. **재생 직전에 효과음 볼륨을 조회**한다 | 볼륨 값을 자기 필드에 캐시 |
| `SettingsUI` | ClientOnly | 슬라이더 표시·입력 전달 | 볼륨 값을 자체 보관 |

### 1.1 왜 `@Logic`인가

AGENTS.md "Script lifecycle" 스코프 규칙 — *"맵을 옮겨도 계속 돌아야 하는가?"* 에 **예**다.

- **BGM은 맵 전환에 끊기면 안 된다.** 맵 `@Component`로 두면 `farm01 → deep_mine` 전환마다 곡이 처음부터 다시 시작한다.
- **볼륨 값도 맵 전환에 살아남아야 한다.** 맵 컴포넌트가 들면 전환할 때마다 기본값으로 되돌아간다.

### 1.2 볼륨의 소유자는 하나다

⚠️ **`MineSoundController.Volume`(현재 상수 `1.0`)에 설정값을 써 넣지 말 것.** 이 컴포넌트는 **맵 3개에 각각 하나씩** 붙어 있어 인스턴스가 3개다. 슬라이더가 그중 하나만 갱신하면 다른 맵에서 옛 볼륨으로 재생되고, 세 개를 다 찾아 쓰면 "누가 진짜 값인지"가 사라진다.

**계약**: `MineSoundController:PlayCue`가 재생 직전에 `_SoundSettingsController:GetSfxVolume()`을 호출해 곱한다.

```
_SoundService:PlaySound(spec.ruid, self.Volume * _SoundSettingsController:GetSfxVolume())
```

`self.Volume`은 **cue 전체의 기준 배율**로 남긴다(Phase 6 청취에서 "전반적으로 시끄럽다"가 나오면 여기를 낮춘다). 사용자 슬라이더와 역할이 다르므로 합치지 않는다 — **`HitFxOffsetY`(연출 의도)와 `ShardPivotOffsetY`(자산 결함 보정)를 일부러 분리한 것과 같은 이유다**(`Archive/As-built.md` 2026-08-06). 합치면 다음에 무엇을 다시 재야 하는지 알 수 없어진다.

> `_SoundSettingsController`가 아직 초기화 전이면(`nil`) **1.0을 가정하고 재생한다.** 컴포넌트 초기화 순서는 보장되지 않으므로 오류가 아니라 기본값이다 — `MineSoundController`가 `self._T.cues == nil`을 침묵으로 처리하는 것과 같은 방침이다.

## 2. 볼륨 모델

### 2.1 값의 정의

| 항목 | 범위 | 기본값 | 적용 대상 |
|---|---|---|---|
| **배경음(BGM) 볼륨** | `0.0` ~ `1.0` | **0.8** (C220 — 초안 0.5 대체) | `_SoundService`의 BGM 채널 |
| **효과음(SFX) 볼륨** | `0.0` ~ `1.0` | **0.7** (C220 — 초안 1.0 대체) | F5 §4의 cue 7종 **전부** |

- 화면에는 **0~100%**로 표시하고 내부값은 `0.0~1.0`을 쓴다. 변환은 표시 직전에만 한다.
- ~~BGM 기본값을 0.5로 두는 이유~~ → **2026-08-16 오너 청취(L5·C220)로 0.8 / 0.7 확정** — "효과음은 신호, BGM 은 배경" 초안은 BGM 만 낮췄지만 실청취에서 양쪽 다 움직였다(§9 U3). 이후 이 표의 기본값이 단일 기준이다.
- 두 슬라이더는 **완전히 독립**이다. 한쪽을 0으로 내려도 다른 쪽에 영향이 없다.

### 2.2 경계값 처리

| 상황 | 동작 |
|---|---|
| SFX = 0 | `PlaySound`를 **호출하지 않고 건너뛴다**. 쿨다운 원장(`lastPlay`)도 갱신하지 않는다 — 볼륨을 다시 올렸을 때 첫 cue가 쿨다운에 걸려 삼켜지지 않게 한다 |
| BGM = 0 | `PauseBGM()`. `SetBGMVolume(0)`으로 두지 않는다 — 들리지도 않는 곡을 계속 디코딩할 이유가 없다 |
| BGM 0 → 0 초과 | `ResumeBGM()` + `SetBGMVolume(v)`. **`PlayBGM`을 다시 부르지 않는다** — 곡이 처음으로 되감긴다 |
| 값이 범위를 벗어남 | `0.0~1.0`으로 **클램프**한다. 슬라이더가 주는 값이지만 프로필에서 읽은 값은 손상돼 있을 수 있다 |

## 3. BGM 채널

### 3.1 API

`Environment/NativeScripts/Service/SoundService.d.mlua` 확인 결과 BGM은 **SFX와 별도 채널**이며 전용 API가 있다. 볼륨 곱셈으로 흉내 내지 않는다.

| 용도 | 메서드 | ExecSpace |
|---|---|---|
| 재생 시작 | `PlayBGM(string id, float volume)` | `Client` |
| 볼륨 변경 | `SetBGMVolume(float volume)` | `Client` |
| 일시정지 / 재개 | `PauseBGM()` / `ResumeBGM()` | `Client` |
| 정지 | `StopBGM(boolean immediately)` | `Client` |
| 재생 중 여부 | `IsPlayBGM()` | **`ClientOnly`** |

### 3.2 재생 시점

- `SoundSettingsController:OnBeginPlay`에서 **1회** `PlayBGM(ruid, bgmVolume)`. 볼륨이 0이면 재생하지 않는다.
- **맵 전환에 개입하지 않는다.** `@Logic`은 `OnMapEnter`/`OnMapLeave`가 **호출되지 않으므로**(AGENTS.md — 작성해도 조용한 죽은 코드다) 애초에 훅을 걸 자리가 없고, 단일 BGM이라 걸 필요도 없다. 맵마다 다른 곡을 쓰기로 바뀌면 `LocalPlayer.CurrentMap` 폴링이 필요해진다(§6.2가 단일 BGM을 권하는 이유 중 하나).
- **`MineSoundController`의 `CurrentMap` 가드는 BGM에 적용하지 않는다.** 그 가드는 "다른 맵의 광맥 cue가 전역 재생돼 들린다"는 Phase 5 함정을 막는 것이고(`Archive/As-built.md` 2026-08-06), BGM은 애초에 전역이어야 맞다.

### 3.3 루프 여부 — ✅ **실측 완료: `PlayBGM`은 반복 재생이다** (2026-08-14)

`.d.mlua`의 `PlayBGM` 설명은 `"Plays background music."` 뿐이고 **반복 재생 여부가 명시돼 있지 않았다.** SFX 쪽에는 `PlaySound`와 별개로 `PlayLoopSound`가 따로 있으므로 1회 재생일 가능성을 배제할 수 없었다. 그래서 재 봤다.

**실측 결과** — `SoundSettingsController`가 `IsPlayBGM()`을 10초 간격으로 찍었다. 잠정곡 `sound-310`은 **141.5초**다.

```
[SoundSettings] bgm probe t=10s  playing=true
... (10초 간격 19건 전부 playing=true) ...
[SoundSettings] bgm probe t=140s playing=true    ← 곡 끝(141.5s) 직전
[SoundSettings] bgm probe t=150s playing=true    ← 곡 끝을 넘겼는데도 재생 중
[SoundSettings] bgm probe closed t=200s playing=true
```

**곡 길이를 58.5초 넘겨서도 끊기지 않았다 → 루프다.** 따라서:

- `PlayLoopSound`로 대체할 필요가 없다.
- **§2.2의 경계값 표가 그대로 유효하다** — 볼륨 제어는 `SetBGMVolume`이고, 0에서 올라올 때 `PlayBGM`을 다시 부르면 곡이 되감긴다는 규칙도 그대로다.
- 자동화 세션이 길어도 BGM이 도중에 사라지지 않는다. Phase 6 청취에서 "곡이 끝나고 조용해진다"를 걱정할 필요가 없다.

> **추정으로 넘어가지 않은 것이 맞았다.** "BGM이니까 당연히 루프겠지"는 이 프로젝트에서 이미 두 번 틀린 종류의 추론이다(C206 부유석 condition, `docs/21` §5 파편 자산 2종 — 둘 다 문서 설명만 믿고 넣었다가 기각). **이번엔 추론이 맞았지만, 맞았다는 것도 실측해서야 알았다.**
>
> **곡을 교체하면 다시 재지 않아도 된다.** 이 실측은 자산의 성질이 아니라 **`PlayBGM` API의 성질**을 재는 것이었다. 프로브는 `ProbeWindowSeconds`(기본 200초) 안에서만 돌고 스스로 닫히므로 로그를 오염시키지 않으니, 새 곡이 200초보다 길면 그 값만 올려 다시 확인하면 된다.

## 4. 저장 계약

### 4.1 구현 전 시간 제약 이력 — 후속 구현으로 해소됨

> 이 절의 전달 시한은 T-02가 병합되며 해소됐다. v8에는 `settings`가 함께 들어갔고, T-12-B는 `settings.tuned` 무버전 확장으로 초안값과 사용자 저장값을 구분한다.

**C214(2026-08-11)로 프로필 저장이 확정됐다.** 이에 따라 `AccountProfile`에 필드가 늘고, 그 필드는 **v8 마이그레이션에 함께 들어가야 한다.**

`docs/17` §0.2-A가 못 박아 둔 것:

> v8 마이그레이션에 **필드 4개**를 함께 넣어야 한다 — `progress.mineLevels` · worker 손 개수 · `currencies.Crystal` · `tutorial`. **나눠서 v9를 만들면 마이그레이션이 두 번 필요해진다.**

T-02는 **2026-08-07에 프로그래머 팀원에게 배정돼 진행 중**이다(`docs/18` §1). 설정 필드가 **5번째**로 들어가려면 **병합 전에 알려야 한다.** 놓치면 v9를 새로 파거나(마이그레이션 2회) 세션 한정으로 후퇴해야 한다.

> **팀원에게 전달할 내용은 이 한 줄이다** — *"v8에 `settings: { bgmVolume, sfxVolume }` 를 추가해 주세요. v7 프로필은 기본값(0.5 / 1.0)으로 채우고, 없으면 변환 실패가 아니라 기본값입니다. 근거 C214 · 계약 `docs/25` §4.2."*

### 4.2 프로필 저장 계약 (C214 확정)

```text
AccountProfile
  settings: bgmVolume, sfxVolume      ← v8에 추가
```

| 항목 | 계약 |
|---|---|
| 위치 | `AccountProfile.settings` (신규 최상위 그룹). 기존 `currencies`/`progress`/`storage` 어디에도 속하지 않는다 — 원장이 아니라 표현 설정이다 |
| v7 → v8 변환 | 필드가 없으면 **기본값(§2.1)으로 채운다.** 변환 실패로 취급하지 않는다 |
| **`tuned` (T-12-B 무버전 확장, 2026-08-18)** | 사용자가 슬라이더로 저장한 적이 있는지. **false(또는 누락)면 저장된 볼륨을 버리고 §2.1 설계 기본값을 쓴다** — T-02 마이그레이션이 슬라이더 도입 전 초안값(0.5/1.0)을 박아 둬서, 이 구분 없이는 C220 확정 균형이 기존 계정에서 무시된다. `RequestUpdateSoundSettings` 저장 시 처음 true 가 된다. 스키마 v8 유지(누락 시 기본값 — `pendingOreCount` 와 같은 방식) |
| 저장 시점 | 슬라이더를 **놓았을 때 1회**(드래그 중 매 프레임 저장 금지). 저장 실패해도 **현재 세션의 볼륨은 유지**하고 경고만 남긴다 — F7-A §3의 "접속 중 저장 실패는 플레이를 멈추지 않되 경고 상태를 남긴다"와 같다 |
| 값 검증 | 서버는 `0.0~1.0` 클램프만 한다. **거절하지 않는다**(§4.3) |

### 4.3 서버 거절 사유를 만들지 않는다

`docs/23`(F8)은 거절 사유에 안정 코드를 부여하지만, **볼륨 설정에는 거절 경로를 만들지 않는다.** 볼륨은 재화·원장·소유권 어느 것도 건드리지 않아 "거절해야 할 요청"이라는 개념이 없다. 범위를 벗어난 값은 거절이 아니라 **클램프**다. `docs/23`에 이 화면의 행을 추가하지 않는다.

## 10. 계정 데이터 초기화 (2026-08-23 오너 요청)

설정 패널 하단(튜토리얼 다시 보기 아래)에 `BtnDataReset` — **"계정 데이터 초기화"** (300×64, `button-slate-blank`, 진홍 글자로 파괴적 동작 구분). Panel 은 480→580 高, `BtnClose` 는 `(0,-480)`.

- **확인 절차**: 클릭 → 공용 `_UIPopup` 확인 팝업(경고: "처음 상태로 되돌아가며, 되돌릴 수 없습니다") → 확인 시에만 `AccountProfileService:RequestProfileReset()`. 팝업은 GroupOrder 10 이라 설정 모달(8) 위에 뜬다 (§5.2 표와 정합).
- **서버 계약** (`ResetProfileToDefault`, ServerOnly): `CanWriteProfile()` 게이트. 직전 저장본을 `RecoveryArchiveStorageKey`(`maple-digger.account.recovery-archive.v1`) 로 아카이브(1세대 안전망 — `AbandonCorruptProfile` 과 같은 키), 본 저장본+백업을 `CreateDefaultProfile()` 값으로 `TransactSetAndWait`. **저장 성공 뒤에만 메모리 프로필을 교체한다** — 실패 시 아무것도 변하지 않고 "초기화 저장에 실패했습니다. 계정 데이터는 그대로입니다." 안내(`LastTransactionMessage` → §52-7 전역 팝업 채널).
- **초기화 후 런타임**: 잉여 일꾼(Worker02~05)을 세 광산 맵 전부에서 Destroy → @Sync 미러 재동기화 → farm01 복귀 + 일꾼 1 재구성(`RestoreLastMineAndWorker` 재사용) → 사운드 설정은 미러(0.8/0.7)를 본 설정 패널 감시가 즉시 재적용 → **튜토리얼 자동 시작**(step=0, `TutorialController` 기존 E1·E14 감시 — 별도 코드 없음).
- **거절 사유를 새로 만들지 않는다** (§4.3 과 같은 방침): 실패는 저장 실패 안내 하나뿐이고 `docs/23` 에 행을 추가하지 않는다 — 원장을 지우는 행위 자체가 사용자의 명시 확인을 거친다.
