# F7-B. 경제 · 진행 기능 명세

> D3/D7의 판매·보호 수량·광산 진행·일꾼/수레 강화 계약을 구현 책임으로 분리한다. 모든 수량과 비용 판정은 서버가 수행하며, 영구 반영은 F7-A를 통해서만 한다.
> 최신화: 2026-07-29 — §5 맵 강화를 D7 §4.2/§5.3에서 끌어와 구현 계약으로 정합화했다.

## 1. 구성 요소와 책임

| 구성 요소 | 책임 |
|---|---|
| `EconomyService` | 판매 단가, 골드·토큰 지급, 보호 수량·자동 판매 판정 |
| `ProgressionService` | 광산 해금/강화, 일꾼 구매, 수레 강화 조건과 비용 |
| `AccountProfileService` | 성공한 거래의 영구 저장과 실패 시 롤백, 강화 레벨 원장 |
| `VeinTickSimulator` | 맵 강화 효과를 광맥 회복·희귀 판정·특별 광맥 스폰에 적용 |
| 클라이언트 상점/HUD | 현재 보유량·조건·예상 결과를 표시하고 요청만 전송 |

## 2. 판매와 자동 판매

- 일반 광물 `stone`/`iron`/`gold`만 수동·자동 판매 대상이다. 초기 단가는 각각 1/5/20 골드이며 Play 테스트 전 제안값이다.
- 수동 판매는 수량 입력과 `1/10/100/전량`을 제공한다. 서버는 요청 수량이 보유량을 넘지 않는지 확인한다.
- 자동 판매는 광물별 토글과 보호 수량을 사용한다. 보호 수량 초과분만 판매한다.
- 다음 광산 해금에 필요한 일반 광물은 정확히 필요 수량만 보호한다. 보호분 판매 요청은 경고 확인 뒤 허용한다.
- 희귀 광물은 창고 하역 순간 별도 희귀 광물 컬렉션에 등록하고, 그 등록으로 계정 패시브를 누적한다. 해당 종류가 컬렉션 10단계에 도달하기 전에는 판매할 수 없다. 11회째부터 플레이어가 설정했을 때만 판매하며, 희귀 돌 50골드·희귀 철 200골드·희귀 금 600골드를 지급한다.
- 희귀 돌은 수레 용량, 희귀 철은 광맥 회복 속도, 희귀 금은 일반 광물 판매 가격을 단계당 +3%씩 강화한다. 희귀 광물 확률은 맵 강화 전용 효과다.

판매 보상, 토큰 전환, 자동 판매 여부는 서버가 하나의 거래로 계산·저장한다. UI는 성공한 결과만 강조한다.

## 3. 진행과 강화

| 항목 | 확정 규칙 |
|---|---|
| 광산 해금 | 골드 + MineToken + 특정 일반 광물 납품, 입장 반복 비용 없음 |
| 광산 강화 | 맵별 레벨 0~10, 골드 + 해당 대표 광물 (상세 계약은 §5) |
| 일꾼 구매 | 1명 시작, 최대 5명; 골드와 진행 조건/광물 납품 |
| 수레 강화 | 일꾼별 기본 20에서 +2씩 최대 50, 골드 + 대표 광물 |
| 도감 보너스 | 수레 강화 최대치와 별도 합산; F7-D가 계산한 값을 사용 |

각 광산의 **대표 광물**은 초보 광산 `stone`, 깊은 광산 `iron`, 보석 광산 `gold`이다. 수레 강화·맵 강화·토큰 환산이 모두 이 정의를 공유한다.

D7의 비용 표는 첫 Play 테스트 제안이다. 값을 바꿀 때는 D7과 D8 변경 기록을 함께 갱신한다.

## 4. 광산 전환

1. 서버는 해금 여부를 검증한다.
2. 현재 광산의 모든 일꾼 프로그램을 먼저 정지한다.
3. F7-A가 보존할 계정 상태를 저장하고, F6이 새 맵 레이아웃을 시작한다.
4. 새 맵의 일꾼은 시작점에서 Idle로 대기한다. 자동 실행하지 않는다.

현재 광맥 stage와 특별 광맥은 새 맵으로 전달하거나 저장하지 않는다.

## 5. 맵 강화 (구현 계약)

D7 §4.2와 §5.3에 흩어져 있던 맵 강화 규칙을 구현 단위로 모은다. 이 절이 맵 강화의 단일 기준이다. 세부 결정의 근거는 D8 카드 **C197~C200**이다.

### 5.1 레벨과 저장

| 항목 | 규칙 |
|---|---|
| 범위 | 맵별 레벨 **0~10** (C197). 해금 직후가 레벨 0이고 보너스는 0이다 |
| 강화 횟수 | 레벨 0에서 10까지 총 **10회** |
| 소유 | 계정 공용. 맵마다 독립 레벨 |
| 저장 | `AccountProfile.progress.mineLevels`에 `{ beginner_mine, deep_mine, gem_mine }` 정수로 보관 |
| 초기화 | 미해금 맵도 레벨 0으로 기록한다. 해금 여부는 `deepMineUnlocked`/`gemMineUnlocked`가 따로 판정한다 |

레벨을 0-based로 두는 이유는 "강화한 만큼만 세진다"가 명확하고, 이미 구현된 일꾼 수레 강화(`cartUpgradeLevel` 0~15)와 같은 관례이기 때문이다.

> **스키마 영향**: 현재 프로필은 v7이며 `mineLevels`가 없다. 구현 시 **v8로 올리고**, v7 프로필은 세 맵 모두 레벨 0으로 채워 변환한다. v8은 §5.3의 `yield` 규칙 때문에 일꾼 손 개수 필드도 함께 추가한다. 변환 절차는 F7-A §3을 따른다.

### 5.2 네 가지 효과

모든 광산이 네 효과를 모두 가지며, 광산마다 **주 효과**만 다르다.

| 효과 키 | 대상 | 적용 지점 |
|---|---|---|
| `yield` | 광물 획득량 | `VeinTickSimulator.TryMine` 성공 시 획득 개수 |
| `recovery` | 광맥 회복 속도 | `VeinTickSimulator`의 `recoverElapsed` 증가량 |
| `rareChance` | 희귀 광물 확률 | `VeinTickSimulator.RollRareDrop`의 기준 확률 |
| `specialSpawn` | 특별 광맥 출현 가속 | `SpecialVeinSpawnTicks`(기본 750틱 = 5분) 대기 단축 |

| 광산 | 주 효과 |
|---|---|
| 초보 광산 `beginner_mine` | `yield` |
| 깊은 광산 `deep_mine` | `recovery` |
| 보석 광산 `gem_mine` | `rareChance` |

레벨 `L`(0~10)에서의 보너스 비율은 다음과 같다.

```text
주 효과    bonus = 3 × L %
나머지 3종  bonus = 1 × L %
```

즉 레벨 0에서 전부 0%, 레벨 10에서 주 효과 +30% / 나머지 각 +10%다.

### 5.3 효과별 계산 규칙

효과마다 적용 지점의 자료형이 달라 계산 방식을 개별로 고정한다.

**`recovery` — 연속값 곱**

`recoverElapsed`를 1틱마다 `1.0 × recoveryMultiplier`씩 증가시킨다. 희귀 철 패시브가 이미 같은 지점에 곱해지고 있으므로, 두 배율은 **가산 합성**한다(C198).

```text
recoveryMultiplier = 1.0 + (희귀 철 단계 × 0.03) + (맵 recovery 보너스)
```

깊은 광산 레벨 10(주 효과 +30%)과 희귀 철 10단계(+30%)를 모두 갖추면 `1.60`배다.

**`specialSpawn` — 대기 틱 단축**

```text
effectiveSpawnTicks = max(60, floor(750 / (1 + specialSpawn 보너스)))
```

하한 60틱(24초)은 동시 활성 3개 상한과 함께 스폰 폭주를 막는 안전값이다(C200).

**`rareChance` — 만분율로 승격**

현재 `RollRareDrop`은 정수 백분율(`1` / `5`)과 `RandomIntegerRange(1, 100)`을 쓴다. 이 정밀도로는 1%에 +10%를 적용한 1.1%를 표현할 수 없다.

구현 시 **기준 단위를 만분율(basis point)로 바꾸고** 판정도 `RandomIntegerRange(1, 10000)`으로 옮긴다.

```text
기본값       일반 광맥 100bp(1%) / 특별 광맥 500bp(5%)
적용 후      floor(기본 bp × (1 + rareChance 보너스))
판정         RandomIntegerRange(1, 10000) <= 적용 후 bp
```

기존 테스트 훅 `RareDropTestPercent`도 `RareDropTestBasisPoint`로 함께 옮긴다.

**`yield` — 확률적 추가 지급 (손 계약 변경 있음)**

채굴 1회에 확률로 광물을 **1개 더 지급한다**(C199). 최대 2개다.

```text
채굴 성공 시, 확률 (yield 보너스)로 같은 광물 1개를 추가 지급한다.
단, 희귀 광물로 승격된 채굴에는 추가 지급을 적용하지 않는다.
```

희귀 승격분을 제외하는 이유는, 적용하면 희귀 획득량이 실질 2배가 되어 "희귀 확률은 맵 강화 `rareChance` 전용"이라는 C196 원칙이 무너지기 때문이다.

이 결정은 **D3 §4의 손 1칸 계약을 바꾼다.** 파급 범위는 다음과 같다.

| 대상 | 변경 |
|---|---|
| 손 용량 | 기본 1칸을 유지하되, `yield` 추가 지급이 발동한 경우에 한해 **같은 광물 최대 2개**를 보유한다 |
| `WorkerController.PendingOre` | 현재 단일 문자열이다. `PendingOreCount`(1~2)를 함께 둔다 |
| `mine` 성공 조건 | **변경 없음.** 손이 완전히 빈 상태에서만 채굴한다. 손에 1개든 2개든 남아 있으면 실패한다 |
| `load` | 손의 전량을 수레로 옮긴다. 수레 여유가 1칸뿐이면 1개만 싣고 나머지 1개는 손에 남긴다 |
| `cart_full` / `hand_empty` 조건 블록 | 판정 기준은 그대로다. `hand_empty`는 개수 0을 뜻한다 |
| 저장 | v8 프로필의 worker record에 손 개수를 추가한다 (F7-A §2.1) |

D3 §4의 운반 상태 전이표도 이 규칙으로 갱신한다.

### 5.4 비용

레벨 `L`에서 `L+1`로 올릴 때의 비용이다. `n = L + 1`(1~10)로 둔다.

```text
골드      round(30 × 1.35^(n-1))
대표 광물  20 × n
```

레벨 0→1이 골드 30 + 대표 광물 20이고, 레벨 9→10이 골드 447 + 대표 광물 200이다. 레벨 0에서 10까지의 누적은 골드 약 1,638 + 대표 광물 1,100개다. D7 §5.3의 첫 테스트 제안을 그대로 쓰며, Play 테스트로 조정한다.

강화는 **해당 광산에 입장한 상태에서만** 요청할 수 있다. 대표 광물이 광산에 종속되기 때문이며, 수레 강화(F7-B 기존 구현)와 같은 제약이다.

### 5.5 서버 API 계약

| API | 호출자 | 결과 |
|---|---|---|
| `ProgressionService.GetMineUpgradeCost(mineId, level)` | UI / 내부 | 다음 레벨의 골드·대표 광물 비용. 이미 레벨 10이면 실패 사유 반환 |
| `ProgressionService.RequestMineUpgrade(player)` | 클라이언트 | 현재 입장 광산의 레벨을 1 올린다. 레벨 상한·재화·입장 여부를 서버가 검증 |
| `AccountProfileService.PurchaseMineUpgrade(mineId, goldCost, oreType, oreCost)` | ProgressionService | 저장 성공 뒤에만 비용 차감과 레벨 증가를 확정. 실패 시 스냅샷 롤백 |
| `AccountProfileService.GetMineBonus(mineId, effectKey)` | VeinTickSimulator | 해당 맵·효과의 보너스 비율(주 효과 0.0~0.30, 부 효과 0.0~0.10) |

`VeinTickSimulator`는 매 틱 프로필을 조회하지 않는다. 맵 진입 시와 강화 성공 시에만 네 보너스를 캐시하고, 강화 성공 시 서버가 현재 맵 시뮬레이터에 갱신을 통지한다.

레벨은 `@Sync` 읽기 전용 값으로 클라이언트에 내려 광산 선택 화면(D7 §4.2, C148)이 표시한다.

### 5.6 화면 표기 규칙

> 신설: 2026-07-30. §5.5의 서버 API만으로는 "화면에 무엇을 어떻게 쓸지"가 정해지지 않아 UI 구현(T-03)이 막혀 있었다. 이 절이 맵 강화 표기의 단일 기준이다.

#### 5.6.1 누적값을 쓴다

레벨당 증가분(주 효과 +3%)이 아니라 **현재 누적 보너스**를 쓰고, 강화 후 값을 `→`로 나란히 보여 준다. 증가분만 쓰면 플레이어가 현재 능력치를 알 수 없다(레벨 4에서 `+3%`는 틀린 정보이고 `+12%`가 맞다).

```text
초보 광산                         Lv.4 / 10
──────────────────────────────────────────
획득량   (주)   +12%  →  +15%
회복 속도       +4%   →  +5%     (5.0틱 → 4.8틱)
희귀 확률       +4%   →  +5%     (104bp → 105bp)
특별 광맥       +4%   →  +5%     (5분 0초 → 4분 46초)
──────────────────────────────────────────
다음 강화: 골드 89 · 돌 100
```

- **4효과를 항상 4줄로** 보여 준다. 주 효과에만 `(주)` 표시를 붙여 광산마다 다르다는 것을 전달한다.
- 레벨 10에서는 `→` 열을 지우고 `최대 레벨`로 대체한다.

#### 5.6.2 체감이 어려운 효과는 절대값을 병기한다

`특별 광맥 +4%`가 몇 초 빨라지는지는 백분율만으로 알 수 없다. **서버가 실제 판정에 쓰는 값**을 그대로 병기한다.

| 효과 | 병기할 절대값 |
|---|---|
| `recovery` | 회복 소요 틱 (`recoverTicks / recoveryMultiplier`) |
| `rareChance` | 적용 후 만분율 (`bp`) |
| `specialSpawn` | `effectiveSpawnTicks`를 분·초로 환산 |
| `yield` | 추가 지급 확률 (%) — 별도 절대값 불필요 |

#### 5.6.3 클라이언트는 재계산하지 않는다

F5 §5.3의 원칙을 맵 강화에도 그대로 적용한다. **서버가 계산한 값을 그대로 표시**하고 클라이언트에서 `%`를 다시 계산하지 않는다.

이유는 이미 겪은 사례가 있다 — 희귀 돌의 수레 보너스는 `floor(기본 × 단계 × 3 / 100)` **버림**이라 단계마다 +1칸이 아니다(관측값 20, 21, 21, 22, 23, 23, 24, 24, 25, 26). 클라이언트가 `%`로 재계산하면 서버 값과 어긋난다. `rareChance`의 만분율 승격(§5.3)과 `specialSpawn`의 `floor` + 하한 60틱도 같은 성질이다.

#### 5.6.4 희귀 패시브와 합산되는 효과는 합성 결과를 보여 준다

`recovery`는 맵 강화와 희귀 철 패시브가 **가산 합성**된다(C198). 둘을 따로만 보여 주면 플레이어가 곱셈으로 착각한다.

```text
회복 속도       +4%   →  +5%     (희귀 철 +9% 합산 → 1.13배)
```

#### 5.6.5 서버가 내려보낼 값 (`@Sync`)

§5.6.3 때문에 아래 값은 **모두 서버 계산 결과**여야 한다. `AccountProfileService` 또는 맵의 `VeinTickSimulator`에서 `@Sync`로 내려보낸다. T-02 구현 범위에 포함한다.

| 값 | 용도 |
|---|---|
| 맵별 현재 레벨 | `Lv.n / 10` |
| 4효과의 **현재** 누적 보너스 | `+12%` |
| 4효과의 **다음 레벨** 누적 보너스 | `→ +15%` |
| 현재·다음 `effectiveSpawnTicks` | `5분 0초 → 4분 46초` |
| 현재·다음 적용 후 `rareChance` bp | `104bp → 105bp` |
| 희귀 패시브 합성 후 최종 `recoveryMultiplier` | `1.13배` |
| 다음 레벨 비용 (골드 · 대표 광물) | `골드 89 · 돌 100` |

레벨 10에서는 "다음 레벨" 값들을 보내지 않거나 현재값과 동일하게 보내고, 클라이언트가 `최대 레벨`로 표기한다.

### 5.7 실패 처리

- 저장 실패 시 레벨과 비용을 모두 이전 상태로 되돌린다(F7-A §3).
- 레벨 10에서의 추가 요청은 차감 없이 거절하고 "최대 레벨입니다"를 표시한다.
- `yield` 추가 지급으로 손에 2개가 있는 상태에서 저장이 끊겨도, 복구 시 손 개수를 그대로 되살린다. 개수 필드가 없는 v7 기록은 1개로 변환한다.
- 미해금 광산의 강화 요청은 거절한다. 입장 자체가 불가능하므로 정상 경로에서는 도달하지 않는다.
