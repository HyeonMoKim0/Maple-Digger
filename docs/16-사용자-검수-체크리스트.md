# 사용자 검수 체크리스트

> 기준일: 2026-07-31
> 목적: 코드·Maker 로그 검증과 사용자의 실제 조작/시각 검수를 구분한다. 이 문서는 기능 기획서가 아니라, 현재 구현이 기획대로 플레이되는지 확인하는 실행 기록이다.
> **현황: 화면 결함 D-1 ~ D-13 전량 해소, 미해결 0건.** §11~§16이 D-1~D-12, §17이 D-13(엔진 재저장 회귀)이다.

## 1. 기록 방법

- 각 항목은 `통과` / `실패` / `보류` 중 하나로 표시하고, 실패면 재현 순서와 화면/로그를 남긴다.
- `자동 검증됨`은 Maker Build·Play 로그 또는 서버 거래 테스트로 확인한 사실이다. 사용자가 UI를 직접 눌러 본 결과를 대신하지 않는다.
- 아래 미구현 범위(F5, 맵 강화, F7-C, F7-D)는 실패가 아니라 **검수 대상 제외**다.

| 상태 | 뜻 |
|---|---|
| 자동 검증됨 | 현 코드와 Maker 로그에서 확인됨 |
| 사용자 검수 필요 | 실제 조작·표시·체감 확인이 필요함 |
| 자동화 불가 | 도구 한계로 자동 검증이 원천 불가능한 항목 (§9 참조) |
| 실패 | 확인 결과 기획과 어긋남 |
| 대상 제외 | 아직 구현하지 않은 기획 범위 |

## 7. 2026-07-29 2차 자동 검수 기록

### 7.1 빌드·초기화

- `refresh` 후 Build Console은 16건 전부 `Info` 등급(LIA 정적 분석 안내)이며 **오류·경고 0건**이다.
- Play 초기화 로그: `[VeinTick] layout loaded mineId=beginner_mine veins=4 starts=5 specialCandidates=3 depot=(0,0)`, marker 8건(depot 1 / normal 4 / special 3) 등록, `[VeinTick] worker registered count=1`, `[Worker 1] spawned at cell (0,0) state=Idle`, `[Worker 1] configured cart=0/20 hand=`.
- 종료 시 `final save complete` → `session lock released` 순서를 확인했다.

### 7.2 희귀 광물 서버 거래 테스트

`server_main` 컨텍스트에서 `AccountProfileService` / `EconomyService`를 직접 호출해 §4의 전 항목을 확인했다. 검증 종료 후 개발 프로필을 기준 상태로 원복하고 저장까지 확인했다: `[Restore] saved=true gold=0 token=0 ore=0/0/0 coll=0/0/0 store=0/0/0 cart1=20 workers=1 mine=farm01`.

수레 용량은 `floor(기본용량 × 단계 × 3 / 100)`을 더하는 **버림** 방식이라 단계마다 +1칸씩 오르지 않는다. 관측값은 단계 1~10에서 20, 21, 21, 22, 23, 23, 24, 24, 25, 26이다. 이는 "단계당 +3%"의 올바른 구현이며, UI에 단계별 증가량을 표시할 때 이 비선형성을 그대로 보여야 한다.

### 7.3 화면 검수에서 발견한 결함

| # | 증상 | 판정 | 조치 |
|---|---|---|---|
| D-1 | `광산 선택` 버튼이 블록 편집기 패널 헤더와 겹쳐 제목을 가림 | 실패 | `MineSelectUI`/`BlockProgramUI`의 앵커·`displayOrder`를 UIBuilder로 재배치 |
| D-2 | HUD `광산 현황`에 골드·크리스탈·토큰이 없음 | 실패 | D3 §7·D5 §4의 필수 표시 항목이다. `MineInventoryController`/`MineHUD.ui`에 재화 표시를 추가 |
| D-3 | 블록 편집기 패널이 1920×1080 좌측 절반 이상을 점유 | 보류 | 상시 표시가 기획 의도인지 확인 후, 토글식 패널로 바꿀지 결정 |

D-1·D-2는 `MineSelectUI.ui` 정적 lint의 겹침 경고 28건과 별개로 **실제 Play 화면에서 재현된 결함**이다.

- **초기화·저장·세션**: 통과. v7 프로필 로드부터 종료 저장·잠금 해제까지 정상이다.

- **바인딩**: 통과. `tools/audit_bindings.cjs` 전수 감사에서 UUID 선언 109건 모두 실제 컴포넌트와 일치한다(§15).
- **판매 경로**: 통과. 수량 입력 → 보호 규칙 안내 → 보호분 포함 판매 → 원장 감소·골드 증가·화면 갱신을 §14.2에서 확인했다. **사용자 클릭 검수도 통과**("잘 팔림, 텍스트로라도 표기하니 잘 보임").
- **자동화 루프**: 통과. 채굴 → 손 → 수레 → Depot → 계정 창고 반영과 광맥 회복을 §14.3에서 확인했다.
- **직접 조작 회귀**: 미완료. §9의 도구 한계 때문에 사용자가 직접 수행해야 한다.

다음 작업은 D-7(인벤토리 팝업의 F5 §5.2 I2~I5)과 §12.2 말미의 사용자 직접 검수다. 표시 기준은 `docs/08-비주얼-사운드-기능명세.md`(F5) **§5 HUD 표시 계약**과 **§6 화면 영역 분할 규칙**이며, 착수 순서는 `docs/17-Claude-인수인계.md` §0.2에 있다.

## 9. 자동화 불가 항목의 근거

Maker MCP의 `mouse_input`은 **엔진이 관리하는 UI 요소(`ButtonComponent` 등 표준 이벤트 시스템을 경유하는 버튼·입력 필드)를 클릭하지 못한다.** 2026-07-29 검수에서 `광산 선택` 버튼 좌표로 클릭을 주입했으나 화면 상태가 변하지 않는 것을 확인했다.

따라서 다음은 **영구적으로 사용자 직접 검수 항목**이며, 자동 검증으로 대체할 수 없다.

- 모든 UI 버튼 클릭 회귀 (판매, 자동 판매 토글, 희귀 팝업 열기/판매, 광산 이동, 일꾼 구매, 수레 강화, 블록 조립·실행)
- 텍스트 입력 필드(수량 입력, 자연어 명령창) 입력
- 클릭 결과로만 열리는 화면의 배치·가독성

대신 다음 두 경로는 계속 자동 검증한다.

1. **서버 규칙**: `maker_execute_script`(`server_main`)로 도메인 서비스 메서드를 직접 호출해 원장·거절·저장을 확인한다.
2. **상시 표시 화면**: `maker_screenshot`으로 HUD·상시 패널의 배치와 표시 항목을 확인한다.

## 14. 2026-07-30 D-10·D-11 — 판매가 아예 되지 않던 원인

"판매 실행: 안 됨" 보고를 추적해 결함 2건을 찾았다. 하나는 **속성 타입 오선언**이고 하나는 **피드백 부재**다.

### 14.1 D-11 — 속성 타입 오선언으로 컴포넌트가 런타임 nil (근본 원인)

`MineSelectController`의 속성 3개가 실제 엔티티의 컴포넌트 타입과 달라 런타임에 **nil**이었다. 런타임 확인:

```
[Bind] saleAmountInput=nil  protectedAmountInput=nil  workerStatusText=nil
```

| 속성 | 선언했던 타입 | 엔티티의 실제 컴포넌트 | 증상 |
|---|---|---|---|
| `saleAmountInput` | `TextInputComponent` (레거시) | `TextGUIRendererInputComponent` | **수량을 쓰지도 읽지도 못해 판매가 항상 "판매 수량은 1 이상이어야 합니다."로 실패** |
| `protectedAmountInput` | `TextInputComponent` (레거시) | `TextGUIRendererInputComponent` | 보호 수량 입력·저장 불가 |
| `workerStatusText` | `TextGUIRendererComponent` | `TextComponent` (레거시) | 일꾼 구매 상태가 갱신되지 않음. `.ui`에 적힌 초기 문구가 그대로 보여 정상처럼 착각하게 만들었다 |

`빠른 버튼 1/10/100/전량`은 `saleAmountInput.Text`에 값을 쓰는데, 그 참조가 nil이라 **아무 일도 일어나지 않았다**. 수량은 영원히 0이고 판매는 100% 실패한다. 이것이 "판매 실행 안 됨"의 진짜 원인이다.

수정: 세 속성의 선언 타입을 실제 컴포넌트에 맞췄다(`ReadNonNegative`의 파라미터 타입도 함께).

> **교훈**: `property <Type> x = "<uuid>"`는 `entity:GetComponent(Type)`으로 해석된다. **타입이 틀리면 오류 없이 nil**이 되고, `if x ~= nil` 가드가 있으면 그 기능이 조용히 사라진다. 빌드 로그에도 안 잡힌다. `.ui` 엔티티의 `componentNames`를 확인해 선언 타입을 맞출 것. `textInput()`은 `TextGUIRendererInputComponent`를, 오래된 `.ui` 엔티티는 레거시 `TextComponent`를 가질 수 있다.

### 14.2 D-10 — 거래 결과·거부 사유가 판매 화면에 표시되지 않음

서버는 거부 사유를 `LastTransactionMessage`에 담지만, 그것을 그리는 `FeedbackText`는 **`SelectPanel`에 있다.** §13.1(D-8)에서 판매 패널을 열 때 `SelectPanel`을 끄도록 고친 뒤로는 그 메시지가 화면에서 사라졌다 — D-8이 만든 회귀다.

또 요약이 `설정 보호 0`만 보여 줬다. 서버가 판정에 쓰는 값은 `max(설정 보호, 다음 광산 해금 필요량)` = **120**인데 화면은 0이라, 보호 때문에 막힌 것을 알 방법이 없었다.

수정:

- `AccountProfileService`에 `StoneEffectiveProtection` / `IronEffectiveProtection` / `GoldOreEffectiveProtection` `@Sync`를 추가하고 `SyncRuntimeState`에서 `_EconomyService:GetEffectiveProtection`으로 채운다(런타임 전용, 저장 대상 아님).
- 요약을 `보유 5 | 보호 120 (설정 0)` / `지금 팔 수 있는 수량 0` 형태로 바꿨다. 광물명도 `stone` → `돌`로 표시한다.
- **판매 패널 전용 피드백 줄(`SaleFeedback`)을 신설**했다. 서버 메시지, 로컬 힌트, 그리고 "보유 전량이 보호 수량이라 팔 수 없다 → `보호분 포함 전환`을 먼저 누르라"는 안내를 표시한다.
- `localSaleHint`가 한 번 설정되면 계속 남아 이후 서버 메시지를 덮던 문제도 고쳤다(광물 선택·수량 변경·보호 토글·판매 시도에서 초기화).

**검증**(Play, 실제 핸들러 호출):

| 시나리오 | 결과 |
|---|---|
| 바인딩 | 3개 속성이 모두 정상 컴포넌트로 해석 |
| 수량 입력 | `[MineSelectUI] sell request ore=stone amount=10` — 빠른 버튼 `10`이 반영됨 |
| 보유 초과 판매 | 화면에 `보유 수량보다 많이 판매할 수 없습니다.` 표시 |
| 보호분 미포함 판매 | 요약이 `보호 120 (설정 0)` / `지금 팔 수 있는 수량 0`을 보여 주고, 피드백이 `보호분 포함 전환`을 안내 |

빌드 오류 0건. 검증 후 개발 프로필 원복: `gold=0 stone=1 workers=1`.

### 14.3 채굴·적재·하역 — 자동 검증됨

"되는지 확인이 어렵다"는 보고는 **F5 연출이 미구현**이라 월드에서 진행을 읽을 수 없기 때문이다(§6 대상 제외). 기능 자체는 정상임을 프로그램 실행으로 확인했다.

초보 광산은 Depot `(0,0)`, 일꾼 시작 `(0,0)`, 돌 광맥 `(1,0)` `(2,0)` `(2,-1)` `(3,-1)`이다. `동 E → 채굴 M → 적재 L → 서 W → 하역 U` 5블록을 실행한 로그:

```
[Worker 1] RunProgram accepted blocks=5 - state=Running
step=1 move E -> cell (1,0)        [VeinTick] mined cell 1,0 ore=stone stage=2
step=2 mine stone -> hand at (1,0) step=3 load stone cart=1/20
step=4 move W -> cell (0,0)        [AccountProfile] credited ore=stone count=1
step=5 unload count=1 depotStone=1 [Worker 1] program finished
[VeinTick] recovered cell 1,0 ore=stone stage=3
```

채굴 → 손 → 수레 → Depot → **계정 창고 반영(`credited`)** 과 광맥 회복까지 전부 정상이다. 진행을 눈으로 읽으려면 F5 연출(광맥 stage 스프라이트·행동 이펙트·사운드) 구현이 필요하며, 그때까지는 HUD의 `일꾼 손` / `일꾼 수레` / `창고` 숫자 변화가 유일한 확인 수단이다.

## 15. 2026-07-30 바인딩 전수 감사와 D-12

D-11이 "선언 타입이 틀리면 조용히 nil"이라는 부류의 결함임이 드러났으므로, 같은 유형이 더 있는지 **전수 감사**했다.

### 15.1 감사 방법

`tools/audit_bindings.cjs`를 신설했다. `RootDesk/MyDesk`의 모든 `.mlua`에서 `property <Type> <name> = "<uuid>"` 선언을 뽑고, `ui/*.ui`(UIBuilder)와 `map/*.map`(MapBuilder)의 모든 엔티티를 UUID로 색인해 **선언 타입이 그 엔티티의 `componentNames`에 실제로 있는지** 대조한다.

```bash
node tools/audit_bindings.cjs
```

`.mlua` 19개 / UUID 선언 109개 / 엔티티 197개를 검사한다. 화면 작업 뒤 이 스크립트를 돌리면 nil 바인딩을 즉시 잡을 수 있다.

### 15.2 감사 결과 — D-12 (추가 5건)

| 결과 | 건수 |
|---|---|
| 선언 타입 ≠ 실제 컴포넌트 (런타임 nil) | **5건** |
| UUID를 `.ui`/`.map`에서 찾지 못함 | 0건 |
| 정상 | 104건 |

5건은 모두 `BlockProgramController`의 워커 칩 라벨이다.

| 속성 | 선언했던 타입 | 실제 컴포넌트 |
|---|---|---|
| `worker1ButtonText` ~ `worker5ButtonText` | `TextGUIRendererComponent` | `TextComponent` (레거시) |

`SetWorkerButtonLabel`이 `if label == nil then return end`로 조용히 빠져나가 **워커 탭 라벨이 한 번도 갱신되지 않았다.** 어느 일꾼이 선택됐는지, 어느 일꾼이 미보유인지 화면으로 알 수 없었다.

**추가로 발견한 시각 결함**: 칩의 글자색과 배경색이 모두 `rgba(1,1,1,1)`(흰색)이었다. 바인딩을 고쳐도 **흰 글자가 흰 배경에 묻혀 보이지 않는다.** 스크린샷에서 칩 5개가 빈 흰 박스로 보였던 이유가 이것이다.

수정:

- 5개 속성과 `SetWorkerButtonLabel`의 파라미터 타입을 `TextComponent`로 맞췄다.
- 칩 배경을 팔레트 버튼과 같은 어두운 색(`rgba(0.16, 0.18, 0.24, 1)`)으로 바꿨다.
- 칩이 64×52뿐이라 `일꾼 N (미보유)`가 들어가지 않으므로 라벨을 **번호 + 짧은 표식**으로 줄였다: 일반 `1`, 선택 `[1]`, 미보유 `1 X`. 선택 결과는 피드백 줄이 문장으로 알려 준다. `BestFit`(12~20)도 켜서 폭을 넘지 않게 했다.

**검증**: 바인딩 5개가 `TextComponent`로 정상 해석되고, Play 화면에서 칩이 `[1] 2 X 3 X 4 X 5 X`로 읽힌다(1번 선택, 2~5번 미보유). 감사 재실행 결과 **실패 0건 / 정상 109건**. 빌드 오류 0건.

개발 프로필은 baseline으로 복원하고 새 세션에서 재확인했다: `[FreshSession] gold=0 stone=1 token=0 workers=1 cart1=20`.

## 17. 2026-07-31 D-13 — 엔진 재저장이 되돌린 `GroupOrder` 계층 (회귀)

**D-1 ~ D-12와 성격이 다르다.** 사람이 만든 결함이 아니라 **Maker의 엔진 업그레이드 재저장이 이미 고친 값을 되돌린 회귀(regression)** 다. 같은 일이 재발할 수 있으므로 감시 대상으로 남긴다.

### 17.1 무엇이 일어났나

`ui/` 8개와 `map/farm01.map`이 미커밋 상태로 남아 있었다. 파일 mtime이 전부 `2026-07-30 08:27:14` 1초 안이고 내장 `CoreVersion`이 `26.5.0.0 → 26.7.0.0`으로 바뀐 것으로 보아, Maker가 엔진 업그레이드 후 일괄 재저장한 결과다.

diff 8,839줄 중 대부분은 무해한 정규화였다 — `Rotation`/`ZRotation` 필드 추가, `Position`에 앵커 해석값 기입, float32 반올림(`0.10196078431372549 → 0.101960786`), 자식 `displayOrder` 1칸 당김(상대 순서 보존). **그 안에 계층 회귀가 섞여 있었다.**

| 파일 | 커밋된 값 (F5 §6.2 목표) | 재저장 후 |
|---|--:|--:|
| `ui/PopupGroup.ui` | 10 | **3** |
| `ui/ToastGroup.ui` | 20 | **4** |
| `ui/AccountRecoveryUI.ui` | 50 | **6** |

나머지 5개(`DefaultGroup 0` / `BlockProgramUI 1` / `MineHUD 2` / `MineInventoryUI 5` / `MineSelectUI 7`)는 그대로여서 **상대 순서가 깨졌다.** 결과적으로 토스트(4)와 복구 오버레이(6)가 모달(`MineSelectUI` 7)보다 아래로 내려가, D-1·D-3에서 맞춘 계층이 무효화된 상태였다.

### 17.2 왜 눈에 띄지 않았나

- **빌드 로그에 남지 않는다.** 오류도 경고도 없다.
- **바인딩 감사도 통과한다.** UUID와 컴포넌트 타입은 그대로이므로 `audit_bindings.cjs`가 잡지 못한다.
- 증상은 "토스트가 모달에 가린다"인데, 토스트는 특정 이벤트에서만 뜨므로 상시 화면 스크린샷으로도 드러나지 않는다.

| 서버 상태 | `schema=7 gold=0`, `VeinTick veins=4 starts=5 specialCandidates=3`, `Worker 1 cart=0/20`, `owned workers restored count=1` |
| 바인딩 감사 | 실패 0건 / 정상 113건 |
| **`GroupOrder` 런타임 실측** | `maker_execute_script`(client)로 `/ui/<Group>`의 `UIGroupComponent.GroupOrder`를 찍어 **상대 순서가 F5 §6.2 목표와 일치**함을 확인 |

### 17.4 이 건에서 새로 알아낸 엔진 동작 — 앞으로 검증 방법이 바뀐다

**`GroupOrder`의 절대값은 런타임에 남지 않는다.** 엔진이 로드 시 **0..N 밀집 수열로 재압축**한다. 복구 후 파일 값은 `0/1/2/5/7/10/20/50`이지만 런타임 실측은 `0/1/2/3/4/5/6/7`이었다. **상대 순서만 의미가 있다.**

이 사실은 두 가지를 바꾼다.

1. **계층 검증은 파일 값이 아니라 런타임 상대 순서로 판정해야 한다.** 파일에 목표값이 적혀 있어도 그것이 런타임에 그대로 가는 것은 아니다.
2. `Archive/As-built.md`의 2026-07-30 기록에 있던 "현재 `GroupOrder`는 생성 순서대로 0~7"이라는 관측은 **원본 값이 아니라 이 압축된 런타임 값을 본 것**이었다.

### 17.5 같은 날 재발 — 그리고 메커니즘 확정

복구 커밋 직후 Maker가 `.ui` 6개를 **다시 저장했다.** 확인해 보니 `MineInventoryUI 5→3`, `MineSelectUI 7→4`로 바뀌어 있었다. 이때는 **상대 순서가 유지**돼 계층은 깨지지 않았다.

두 사건을 합치면 메커니즘이 보인다. **Maker는 저장하는 `.ui`에 런타임 압축값(0..N)을 그대로 써 넣는다.**

| 상황 | 결과 |
|---|---|
| Maker가 `.ui` **전부**를 저장 | 압축값이 일괄 적용 → **상대 순서 유지, 무해** |
| Maker가 **일부만** 저장 | 저장된 파일은 압축값(작은 수), 나머지는 저자값(큰 수) → **두 척도가 섞여 순서가 깨짐** |

**D-13은 후자였다.** `PopupGroup 10→3` / `ToastGroup 20→4` / `AccountRecoveryUI 50→6`만 압축값을 받고 `MineInventoryUI 5` / `MineSelectUI 7`은 저자값으로 남아, 토스트가 모달 아래로 내려갔다.

### 17.6 재발 방지 — 밀집 수열로 고정

**희소값을 쓰는 한 이 사고는 구조적으로 반복된다.** 그래서 파일 값을 런타임과 같은 **밀집 수열 `0~7`로 정규화**했다(2026-07-31).

```
0 DefaultGroup · 1 BlockProgramUI · 2 MineHUD · 3 MineInventoryUI
4 MineSelectUI · 5 PopupGroup · 6 ToastGroup · 7 AccountRecoveryUI
```

이제 파일 값과 Maker가 쓰는 값이 같으므로 **일부만 저장돼도 척도가 섞이지 않는다.** 부수 효과로 Maker 저장 때마다 생기던 `.ui` diff도 사라진다.

- **Maker에서 작업한 뒤에는 `git status`로 `.ui`/`.map` 재저장분을 여전히 확인한다.** 다른 종류의 회귀가 섞일 수 있다.
- 규칙은 `docs/17` §1의 `.ui` 주의사항 **6·7**에 넣었다.
- 현재 값은 `.builder-work/fix_grouporder.cjs`의 `survey()`로 한 번에 찍어 볼 수 있다. **판정은 항상 상대 순서로 한다.**
- 새 UIGroup을 추가하면 **끝에 붙이거나 전체를 0부터 다시 매긴다.** 희소값으로 자리를 비워 두지 않는다.
